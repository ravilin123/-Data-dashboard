# `conversion.html` 的自有代码

原来是 `conversion.html` 末尾一段 2557 行的内联 `<script>`，按它**已有的 13 段分区注释**
原样切开，一行没改（除下面「唯一的代码改动」那四处）。页面通过

```html
<script type="module" src="/static/js/conversion/main.js"></script>
```

加载。上面那段内联 SheetJS 是普通 `<script>`，先于模块执行，`window.XLSX` 已就绪 ——
只有 `load.js` 读它。

## 两刀接口（T2）

```
readReport(workbook) → Dataset          dataset.js
analyze(dataset, opts) → AnalysisResult analyze.js
```

**上游改版**（列改名、表头行数、sheet 改名、整列消失）只打到前者；
**业务口径**（阈值、归因、播报）只打到后者。

`Dataset` 是纯数据 —— 没有方法、没有 DOM、不留 workbook 引用，
所以测试可以**直接写字面量**，不用为了测一条口径去造 xlsx（`tests/dataset.mjs` 的 [3]）。
形状：

| 字段 | 内容 |
|---|---|
| `periods` | `{日报:{rows,dates,ok}}` 可用性，读自场景维度 |
| `scene` | `{日报:[...]}` 场景维度行 |
| `merchantSite` / `merchantTotal` | `{日报:[...]}` 站点级 / 商户级合计 |
| `dates` | `{日报:[...]}` 倒序，**取自商户维度**（buildMerged 用的那份） |
| `meta` | `{日报:{hasSite,metricNames}}` |
| `drift` | `formatDrift()` 的结果，含 `dodColumn` |

**一次读齐三个周期**：实测 3.2MB 真实报表，`XLSX.read` 本身 2285ms，`readReport` 507ms。
原来每次 `run()` 要重解析一遍（还调两遍 `loadMerchant`）≈530ms —— 急切一次反而更快，
之后切周期、换日期都是零成本。

`baseline.js` 仍直接调 `loadScene()`：它读的是**用户另外选的历史文件**，不是当前 Dataset，
而且只要一个周期的场景行，走 `readReport` 会白解析商户维度。

T3 之后**分析层已完全不碰 store**（`config / util / load / funnel / detect / broadcast /
dataset / analyze` 一个都不 import `store.js`）：基准线经 `opts.baseline/baselineActive` 传入，
播报素材经 `ctx` 参数传入。store 只留在渲染层和界面接线里 —— 计划里说的就是「那层保留不动」。

## 唯一的代码改动：四处跨模块赋值

ES module 里 import 进来的名字**不能赋值**（是硬报错，不是警告）。原来有四处
在别的分区里直接改另一个分区的 `let`，只能改走 setter：

| 被改的量 | 定义在 | 谁在改 | 改成 |
|---|---|---|---|
| `PERIOD` | `config.js` | `main.js` 两处 | `setPeriod()` |
| `LEVEL_THRESHOLDS` | `config.js` | `main.js` `#recalc` | `setLevelThresholds()` |
| `bcMode` | `render/broadcast.js` | `main.js` `#bcTabs` | `setBcMode()` |

读的一侧不用动：import 进来的是**活绑定**，setter 一改，所有读到的地方都是新值。

## `store.js` 为什么单独存在

`state` 原来定义在第 8 段开头，但 `funnel.js`（`thresholdFor`）、`broadcast.js`、
`baseline.js`、`feishu.js` 都在读它。若把它留在 `render/index.js`，这些模块就都要
反过来 import 渲染层。单拎出来只是为了让依赖方向别拧着。

**T3 已把那四处读取收进参数**（`thresholdFor` / `headlineLines` / `broadcastTxt` /
`broadcastMd`），渲染层保留 store 不动。现在读 `store.js` 的只剩
`main / feishu / baseline / render/*`。

## 共享层 `static/js/shared/`

两个工具页 + 首页共用的东西收在这里（T7）。建它的起因是**同一个函数有三份实现、
行为还不一样** —— 最要命的是 `esc`：conversion 那份 `esc(null)` 给出字面量 `"null"`，
而它有 8 处用在 HTML 属性值上却不转义引号。

| 文件 | 内容 |
|---|---|
| `dom.js` | `$` / `$$` / `esc`（统一取最严：空值→空串，`& < > " '` 全转） |
| `text.js` | `trim` —— 放这里是为了断开 `config ↔ util` 那个环；`shortSite`（去协议头/www./尾斜杠） |
| `theme.js` | `initTheme({onChange})`，含 `crm_theme` 迁移（merchant 那份原来没有） |
| `ai.js` | AI 常量 + `promptSize` / `usageText` / `usageBanner` / 调用栈 |
| `file.js` | `download` |

## 已知的 import 环

切分只是把原来的隐式全局耦合**显式化**，没有新增耦合。T7 之后只剩一个：

```
baseline.js  <->  main.js  <->  render/index.js
```

（`config ↔ util` 靠 `trim` 搬进 shared 断开；`broadcast ↔ render/overview` 靠把
`ptFmt` 挪到 `util.js`、`COUNTER_DIR_FLOOR` 挪到 `config.js` 断开 —— 那两个本来
就不该住在渲染层。`feishu` 也因为 `WB_AI` 改从 shared 拿而出了大环。）

**都是安全的**：环内的跨模块访问全部发生在函数体里（调用时才读），
模块求值期没有任何一处读同一个环里的名字 —— 这一条是用 acorn 逐条核过的，
不是看着像。要改动这几个文件的顶层语句时请重新核一遍。

剩下那个大环是界面接线层内部的（`main` 绑事件要调 `run`，`run` 要回调
`syncDateSel`，`baseline` 面板要触发重算），拆它得先把事件绑定和渲染再分一层，
收益不大，暂不动。

## 环比：现算，源表那列只做校验

告警的环比按**你选的那对日期**现算（`funnel.js` 的 `dodOf()`），和瀑布图、商户下钻、
影响比率同一个口径 —— 以前只有告警读源表那列，一往前翻就是同一屏两套口径（第四轮 A1）。
`computeBaseline()` 和写底账的 `buildDailyRecords()` 也一起改成现算。

源表那列降级成校验：两期相邻时才比，对不上就在概览提示「上游环比口径可能变了」。
解析统一走 `parseDodCell()`，**按形态判不按大小** —— 原来 `Math.abs(d)<1?d:d/100`
把 `1.6154`（+161%）读成 +1.62%、`-1.0`（跌到 0）读成 −1%。

## 只在一期出现的商户 / 来源（A2 + A3）

`buildMerged()` 是**内连接** —— 环比本来就要两期才算得出来。但被它丢掉的那两批
不能就地消失（第四轮 A2）：

| 情况 | 以前 | 现在 |
|---|---|---|
| 上期有量、本期整个没了 | join 掉，任何视图里都没有 | `churn.lost`，按上期 PO 倒序 |
| 本期首次有量 | join 掉 | `churn.gained` |
| 整个来源本期没数据 | 页面上少一张卡，不报错不提示（A3） | `churn.gone`，播报里排在最前 |

「昨天 3000 单今天 0 单」比「某指标掉 2pt」严重得多，而它以前连一行日志都没有。
`buildMerged()` 多返回 `onlyT` / `onlyY`，`buildChurn()` 整理成两张名单，
概览多一块 `#churn` 卡片，播报末尾多一段 `■ 商户进出`。

**两个刻意的取舍**：

1. **小尾巴只计数不点名**（`SMALL_MERCHANT_PO = 50`）。报表里天天有一堆一天几单的
   商户进进出出，全列进群消息会把真正要看的那一两家淹掉。页面上则是前
   `CHURN_TOP = 8` 家直接列、其余收进 `<details>`。
   ⚠️ 群消息里**只报「另有 N 家未列出」，不解释门槛**（2026-09-09）——「不足 50 单
   只计数」是口径不是发现，每期都出现、没人拿它做判断。而且**一家都没列出时连这句
   也不写**：抬头「N 家…上期共 M 单」本身就完整了，再挂一句反而像漏了什么。
   `tests/churn.mjs` 的 [6] 反向钉着（删掉的东西不写用例就会被下次改动加回来）。
2. **本期没走完时要说出来**（`periodIncomplete()`）。周报/月报选到当前这一期时，
   「还没下单」会被算成「掉量」—— 拿真实报表实测，月报（9 月只过了 6 天）能报出
   81 家 / 8.5 万单，几乎全是这个。比率不受影响（它是个比值），所以以前没人被这件事
   咬到，是 A2 把它暴露出来的。不拦着不显示，但卡片和播报里各加一句提醒。

用例 `tests/churn.mjs`（`node` 直接跑）；页面那侧在 `tests/e2e.py` 的 [2b]。

## 折损单量：把各环节折算到同一把尺子上（B1 + B2 + B12）

所有排序原来都在**比率空间**。而 `影响比率 = PO占比 × Δ比率` 里的 pt 是
**该指标自己那一层**的 pt，跨环节根本不可比：

```
对大盘的贡献(pt) = Δ比率 × (该环节分母 / PO总量) × (下游各环节通过率累乘)
影响单量        = Δ比率 × 该环节分母 × 下游各环节通过率累乘      ← 负数 = 少了这么多支付成功单
```

`funnel.js` 的 `downstreamPass()` + `orderImpact()`，`drillMetric()` 产出
`影响单量` / `对大盘影响` 两列并按前者排序。手算例子（同样跌 0.1pt）：

| 指标 | 分母 | 下游 | 影响单量 | 老口径「影响比率」 |
|---|---|---|---|---|
| `2. 业务校验通过率` | 1000 | 0.9 | **−90 单** | −10.0% |
| `4. 网关通过率` | 500 | 1 | **−50 单** | −10.0% |

老口径把这两条判成**一模一样**。`tests/impact.mjs` 的 [3] 钉的就是这个。

⚠️ `downstreamPass()` 用的是**来源级**下游通过率，不是这家商户自己的 —— 商户级的下游值
稀疏又噪，而「这一单过了这个节点之后还要过几关」对同来源的商户基本一致。这是个近似。

⚠️ **摩擦类（3DS 占比那四个）不算折损单量**。占比上升本身不损失单量，损失发生在下游
那几个通过率上；硬套公式会算出一个看着精确、其实没有业务含义的数。那几条退回老的
影响比率排序，`对大盘` 那格显示比率。

### 小样本（B12）

`_small` = 本期不足 `SMALL_MERCHANT_PO`（50）单。三处行为，各有各的理由：

| 地方 | 怎么处理 | 为什么 |
|---|---|---|
| 排序 | **只在算不出折损单量时才沉底** | 折损单量的上界就是这家自己的单量，5 单的商户再怎么崩也只折损 5 单，量级自己压得住；再沉一次，万一它真是当天最大的一笔损失就漏报了。而影响比率没有这个天花板（Δ 能到 80pt），那时候样本量是唯一还站得住的判据 |
| 明细表 | 打「样本少」标记，照常显示 | 真要查某家小商户时它还得在 |
| 播报 | 不点名，末尾统一说一句有几家 | 群消息里的抬头是那个比率（`100.00%→33.33%`），那才是误导人的东西 |

### 重点商户改成「最大的那一处」

`topMerchants()` 原来是把各指标的影响比率**累加**。那些指标本身是父子关系
（`4.2 3DS网关通过率` 和它下面的 `4.2.2`），累加等于把同一批单算两遍 ——
子环节多的商户天然排前面。现在取**最大的那一处折损单量**：不重复计数，
而且直接回答了更有用的问题「这家最严重的一处在哪个环节、值多少单」。

### 用词：「减少 / 增加」，不是「少成 / 多成」

`ordFmt()` 输出的动词是最普通的那两个。「少成」是内部黑话 —— 读的人得先反应一下
「成」指的是成交还是成功。这个数在页面上有列头（`对大盘 · 支付成功单`）撑着，
在播报里有环节抬头（`支付成功单减少 48 单`）撑着，动词写成最普通的那个就够了。

`|值| < 1` 写「减少不足 1 单」而不是「减少 0 单」：真的是零，和四舍五入成零，
在这里是两件事 —— 前者说明这条根本不值得看，后者说明它擦着边。

### 播报里的「解释得了吗」

`本环节共减少 87 单` 底下挂着一家 `减少 1 单`，读的人会以为是算错了。
列出的商户解释不到四成时补一句 `gapNote`：**只把两个数摆出来**
（`上面几家合计−12 单，本环节共−87 单`），不解释差额哪来的 —— 原来那句
「差额来自各商户占比此消彼长，以及不足 50 单未点名的小商户」43 个字、一条播报里
出现两次，2026-09-09 删了。本环节本身不足 5 单时整句不出：那点量不值得解释。
（页面上 `buildSourceStory` 有完整的 reason，受众不一样。）

⚠️ **播报里不许出现「工作台」三个字** —— 那是本机地址（127.0.0.1），群里其他人打不开。
`tests/e2e.py` 的「不含工作台地址」钉着。写新文案时注意，「详见工作台页面」这种顺手
就会写出来（原来 `dropped>0` 那句就是，只是从没触发过所以一直没被抓到）。

## 待观察商户名单（B14）—— 不是告警

`watchlist.js` + `render/watchlist.js`，页面上是 `#watch`，播报里是 `■ 待观察商户`。

**为什么单独一块、样式还刻意不一样**：告警回答「今天出了什么事」，这份名单回答
「这几家要盯着」。它们大多常年低位、环比≈0，任何阈值都不会触发 —— 不做这一段就一个字
都没有。放同一个视觉层级里，人会把它当成一堆没修的告警，然后开始忽略整块。
处理动作和责任人也不一样：前者是排障（查网关、查风控），后者是 BD 去推。

三段：

| 段 | 判据 | 排序 |
|---|---|---|
| 📉 低于同行 | 本期成功率比同来源中位数低 `WATCH_GAP`(10pt)，且 PO ≥ `WATCH_MIN_PO`(10) | 缺口从大到小 |
| 🆕 新入网 | 本期首次有量（就是 A2 的 `churn.gained`，补了成功率） | PO |
| 🔍 量太少 | PO < `WATCH_MIN_PO` | 只报家数和总量，不逐家列 |

### 三个数字为什么是这个值

**门槛 10 单，不是 `SMALL_MERCHANT_PO`(50)。** 量少 + 成功率低正是最该盯的组合 ——
等着被风控关的就是这批，50 的门槛会把他们整批滤掉。但 10 以下不行：1 单 0% 和
1 单 100% 都只是一单的事。那两个常量管的是**两件不同的事**：50 管「这个比率**变动**
可不可信」（B12，告警侧），10 管「这个比率**本身**算不算得出来」（B14）。

**缺口 10pt。** 实测：10pt → 日报 9 家 / 周报 20 家；15pt 只出 5 / 16 家，
会漏掉 `unisilk.shop` 那种 319 单差 11pt 的。

**基准用不加权中位数，不用 PO 加权。** 加权中位数在「一家独大」的来源上会退化成那一家
自己的值 —— Element 只有 4 家、最大一家占 99% 的量，加权基准就是它，于是**谁都不会
低于基准**，整条线没人看着。不加权问的是「一家典型的商户能做到多少」，正是要比的东西。
够量的商户不足 `WATCH_MIN_PEERS`(3) 家时退回「该来源全部商户」，**不跳过这个来源**，
并在界面上标出来（基准是粗的，据它下结论要留余地）。

⚠️ **低位商户自己也算进基准。** 中位数能扛住一半以内的坏样本，剔掉他们反而会让基准虚高、
把整批人都判成「低于同行」。`tests/watchlist.mjs` 的 [4] 钉着这一条。

### 播报是**两条消息**，不是一条

```
【转化率日报监控 2026-09-06】   ← broadcastTxt/Md   今天出了什么事
【待观察商户 2026-09-06】       ← watchTxt/Md       这几家一直不对劲
```

两个理由，都不是洁癖：

1. **两件事、两个受众。** 混在一条里，看的人会把下半截当成没修完的告警，
   然后连上半截一起忽略。
2. **飞书上会很难看。** 一条消息里塞两套结构（环节树 + 三段名单），纯文本版缩进
   层级打架，卡片版更是一大坨。拆开之后各自都短（实测日报：2430 字 + 766 字）。

配套的三处：

| 地方 | 怎么处理 |
|---|---|
| 页面 | 播报面板两块卡片，共用同一个 txt/md 开关（`paintBroadcast()`），各自有复制/下载 |
| 飞书推送 | **串行发两条**，先监控后名单 —— 并发的话群里先后顺序不确定。第一条失败就不发第二条（连不上的话第二条一样连不上） |
| 卡片配色 | 监控有异常红、无异常绿；名单**永远橙** —— 它本来就不是紧急的 |
| 复制 curl | 有两条就复制两条（中间空行隔开）。只给第一条的话，拿去终端跑完还以为全发完了 |

名单空时 `watchTxt/Md` 返回**空串**，界面整块隐藏、推送跳过第二条 ——
每天一条「今天没人要盯」是噪声。

⚠️ 「新入网」那批**只在第二条里**。第一条的「■ 掉量商户」只讲掉量：
掉量是「出事了」，新入网是「要盯着」，不是同一个问题。

⚠️ 群消息里**不写「这不是告警」那种解释句**（用户明确要求删掉）——
标题已经把两条分开了，元信息在群里没人读。解释留在页面卡片上，那是配这套东西的人在看。

### 接出单监控的名单（B15）

出单监控每天已经点过名了 —— 谁刚跨过 $100、谁刚审核通过、谁在滞留。那批正是这份名单
要盯的人，两个工具没必要各判一遍。

```
order_monitor/report.py  save_json()          → data/出单监控结果/出单监控结果_<日期>.json
workbench/order_monitor.py                    → GET /api/order-monitor/latest
main.js 起来时异步取一次 → state.om → analyze(ds,{orderMonitor}) → buildWatchlist
```

走**本机文件**不走多维表格：结果本来就在本机，绕一圈飞书要多一次网络往返、还要处理 token，
而且离线打开工具页时就废了。取不到也不影响任何事 —— `state.om` 是 null 的话名单照样出，
只是少几个标签；取到了而且报表已经加载过，`main.js` 会再调一次 `run()` 补上
（`analyze` 是纯计算，重算几十毫秒）。

⚠️ **只按 `用户ID` 匹配，不按站点。** 站点归一化在 Python（`normalize_site`）和
JS（`shortSite`）各有一份实现，一旦漂移就是**静默匹配不上** —— 这个仓库已经被
「两份实现悄悄不一样」咬过两次（`esc` 三份、漏斗页影子解析）。用户ID 是 19 位整数，
两边格式一致，没有归一化这回事。代价是一个商户有多个站点时会全部命中；
对「这家刚出单，盯一下成功率」这个用途来说没问题。

四类里用三类打标签（`OM_TAGS`），第四类单独成段：

| 出单监控的桶 | 这边怎么用 |
|---|---|
| ✅ 新出单 | 标签「刚出单」 |
| 🐢 小额滞留 / 👀 3天内未出单 | 标签「出单滞留 / 还没出单」 |
| 🆕 新审核通过-待出单 | **单独一段 `omPending`** —— 它们在转化率报表里往往一行都没有（还没交易），上面两段都装不下。这是「在等谁上量」，正是这份名单最该回答的问题之一 |

### 两个容易写错的地方

**排序按缺口（风险），但要单独点一句「最值钱的是谁」。** 缺口小、量大的那家钱最多却排在
末尾 —— 实测周报 `ifonetool.com` 缺口只有 13pt，7031 单，做到中位数一周多成 918 单。
`watch.best` 就是这个用途。

**「连续」要数期数，不是布尔标记。**（`WATCH_LOW_RUN` = 3，用户 2026-09-08 定的：
「这种常年不动的，我理解连续 3 个工作日看到它，就应该被归到待观察商户了」。）

原来只看两期（本期 + 上期），因为 merged 里就这两期。但「常年不动的那批」恰恰要靠期数
才认得出来 —— 两期低可能是巧合，连着三期就是长期低位。现在 `buildWatchlist` 多吃一个
`{dfSite, tDate}`，`runOf()` 从本期往前数：

| 情况 | 怎么处理 | 为什么 |
|---|---|---|
| 那期够量、且低于同行 | 计数 +1 | |
| 那期够量、但**不低** | **断开** | 它那天是好的，连续就断了 |
| 那期单量 < `WATCH_MIN_PO` | **跳过**（不计数也不打断） | 1 单 0% 和 1 单 100% 都是一单，说明不了任何事；但也不该因此否定前后期的连续性 |
| 那期没数据 | 跳过 | 可能压根没下单，不该算成「不低了」 |

⚠️ **基准逐期各算一次**，不能拿本期的基准去卡历史 —— 同行水平自己也在动，
那是另一种口径混用（`tests/watchlist.mjs` 的 [4b] 里「首期同行整体崩」那条钉着）。

⚠️ **关于「工作日」**：数的是**有效期次**不是自然日。周末单量本来就低，上面那条
「单量不足就跳过」已经把它们滤掉大半，所以没有再单独做工作日过滤。实测周末 vs 工作日
的中位差方向混乱（54 个「来源×指标」里 25 个差 ≥1pt，但有的周末高有的低），
样本也不足以下结论 —— 与其按一个站不住的规律切数据，不如让「有效期」这条自然处理。

实测：日报揪出 `insomdrama.com` 连续 8 期（整个数据窗口就没好过）；周报前 10 家
全是长期低位，其中 6 个 evisa 签证站点各 40 单、成功率 2.6%~17.9%、连续 5 期 ——
看着像同一批商户整体有问题。这些以前只标个「连续」，和「这期才掉的」混在一起按缺口排。

## 商户级独立探测（B6）

`merchant_scan.js`。`detect()` 的循环是「遍历场景行 → 触发阈值 → 才拆商户」，
于是**一家中等商户彻底崩了、但被来源大盘稀释到没触发阈值，它在异常明细里完全不存在**。
`topMerchants()` 原来是对已有的 drill 结果做聚合 —— 没进 drill 的，聚合再怎么做也救不回来。

实测周报 2026 W37：整体少成 ≥5 单的 21 家里，**7 家在异常明细里一行都查不到，
合计少成 139 单**。

现在不看场景是否告警，把**每个商户当成一个小漏斗**各算一遍，按「整体少成多少单」排，
Top 6 进「重点关注商户」。

### 两个关键取舍

**1 · 头条数字用源表自己的「业务单支付成功率」，不用累乘值。**
累乘值（`funnelStages` 的 `overallT`）和源表那列在 97 家真实商户里有 2 家对不上 ——
都是个位数单量的脏数据（某个环节是 0 但源表整体不是 0）。源表那列是每家自己的权威值，
而且「低于同行」那段（B14）用的也是它，两处口径必须一致。
累乘只用来**归因**（主因是哪个环节）；对不上时打 `口径存疑` 标记 ——
归因不可全信，别让人照着去查错环节。

**2 · 按整体算，不按单个指标算。**
逐指标算会父子重复计数：`4. 网关通过率` 少成 55 单和 `4.1 非3DS网关通过率` 少成 47 单
是同一批单。`funnelStages` 那套 telescoping 分解是无残差的（各环节贡献相加恰等于整体变动），
按它来既不重复也不遗漏。

### 点卡片会跳去哪

榜上那批「场景级没触发、明细里没有」的商户（卡片标 `明细未覆盖`），点过去只会看到一张空表。
所以按 `data-indrill` 分流：在明细里的走老路径（筛选 + 高亮），不在的**跳「链路精算」**——
那儿有它的完整漏斗，正好回答「这家掉在哪一环」。

## 多期趋势（B5）—— 这个工具的第一张图

`trend.js`（纯函数）+ `render/trend.js`（手写内联 SVG），页面上是 `#trend`。

页面其余部分**只认两期**（T vs Y）。于是一类问题结构性地看不见：每期只掉 0.3pt，
任何阈值都不触发，十期下来掉了 3pt，没有一天会报警。

⚠️ **不用等 B11 的存档接口。** 一份报表里本来就带 8 期日报 / 5 期周报 / 4 期月报，
全在同一个 `dfScene` 里躺着（`loadScene` 读的是整个周期，不是某一天）。
B11 补的是「跨报表的更长历史」，是另一件事。

```
buildTrend(dfScene, {latestDaily}) → {dates, sources, measures, series, po, partial}
                                      series[度量][来源] 是和 dates 等长的数组，缺一期就是 null
```

主图是整体成功率（每个来源一条线），下面 2×2 四张小图对应四个大环节。

### 五个容易画错的地方

**1 · 期次要自然序，不是字典序。** 周报写成 `2026 W9` / `2026 W37`，字典序会把 W9 排到
W37 **后面** —— 折线照画，只是讲了个假故事。`cmpPeriod()` 按数字段比。
（`dataset.js` 里 `dates` 那份仍是字典序，那是下拉框用的，两处目前都对；
真要统一的话改 `dataset.js` 那份，别让 trend 迁就它。）

**2 · 缺一个大环节就断线。** `funnelStages` 缺环节按 1.0 跳过 —— 瀑布图要的就是这个行为，
但拿来画折线就成了「那一期凭空跳高」，而跳上去的那一段**看起来完全正常**。
所以 `overall` 要求四个大环节全都算得出来，否则给 null（线断开）。

**3 · 纵轴不把范围撑到刻度线上。** 第一版撑了：`0.17~0.63` 一撑就是 `0~80%`，
八期数据挤在中间三分之一，上下各空掉四分之一张图。现在刻度取「落在范围内的整数倍」，
数据永远铺满画布，刻度照样是整数。折线本来就不必从 0 起（那是柱图的规矩），
但页面上要**写出来**，免得有人拿两张小图直接比高低。

**4 · 配色独立于品牌色和语义色。** `--s1/--s2/--s3`，浅深各一套，跑过 `dataviz` 的
`validate_palette.js` 六项校验（明度带 / 色度 / 相邻色差 / 色盲下的可分辨 / 对比度）。
语义色四档（`--good/--warning/--serious/--critical`）负责传严重度，拿绿色当「第三条线」
会被读成「这条是好的」。浅色那支绿的对比度 2.82:1 是 WARN —— 校验器说这时候
**必须**有直标或数据表兜底，两样都有（末端直标 + 图例 + 完整数据表）。
⚠️ 取色按 `ALLOWED_SOURCES` 的**下标**，不按本次画了几条线：某个来源整期没数据时，
剩下两条不能跟着换色。

**5 · viewBox 尺寸要贴着真实渲染宽度挑。** viewBox 会连字号一起缩放 ——
第一版取 760 宽，实际拉到 1400px，11px 的轴标签渲染出来 20px，整张图像放大了看。

### 交互

十字光标吸附到最近的期次，**一次列出该期全部来源**的值和单量（指针不必落在某条线上）。
键盘 Tab 进去用左右方向键走，Esc 收起。名字来自源表，tooltip 一律 `textContent` 拼，
不走 innerHTML。末端直标在右缘挤到一起（间距 < 13px）时**整批不画** ——
挪开的标签会脱离它自己那条线，比不画更难读，交给图例和 tooltip。

本期没走完的那一段画**虚线**、期次标 `*`，底下一句说明（复用 `periodIncomplete()`，
和掉量名单那处是同一个判断）。周报/月报选到当前这一期时最后一个点天生偏低，
不标出来会被读成「刚开始掉」。

用例：`tests/trend.mjs`（10 组，`node` 直跑）+ `tests/e2e.py` 的 [2e]。
e2e 那侧钉的是两件在图上看不出错的事：**横轴按时间升序**、
**tooltip 读出来的数等于数据表里那一格**。

## 支付前 / 支付中 两段拆账（B7 后半）

`支付单支付成功率` 在 `KNOWN_UNANALYZED_METRICS` 里躺了很久，一次都没被分析过。

### 它不是一个新指标，是一个新的切法

两条成功率的**分子完全相同**（都是成功单），差别只在分母：

```
业务单支付成功率 = 成功单 / PO单数
支付单支付成功率 = 成功单 / 支付单数        支付单数 = PO单数 × 环节1
```

于是总流失可以**精确**劈成两段，没有残差、不需要任何比率相乘：

```
PO单数 − 成功单 = (PO单数 − 支付单数) + (支付单数 − 成功单)
                =     支付前流失      +     支付中流失
```

实测两份真实报表 **79 组**（来源 × 期次 × 周期）：分子相同 79/79、
`支付单数 = PO单数 × 环节1` 也 79/79 成立，零反例。

### 为什么值得单出一块

**这两段的排查方向完全不同。** 实测 2026-09-06：

| 来源 | PO | 支付前流失 | 支付中流失 | 该找谁 |
|---|---|---|---|---|
| 独立站标准收银台 | 3027 | **1282（42.4%）** | 432 | 收银台 / 前端 |
| 独立站API | 5043 | 65 | **2056** | 风控 / 网关 |
| Element | 5289 | 0 | **4056** | 风控 / 网关 |

同样是「成功率低」，第一家四成的单**根本没走到支付**，后两家是走到了没成 ——
而只看「业务单支付成功率」一个数字，这三家长得一模一样。

⚠️ 计划里原本写的是「两条成功率并排 + 差值走势」。并排看不出该找谁，改成劈单量。

### 四个容易做错的地方

1. **数只从源表的分子/分母来**（`sceneCounts` 的 `_n`/`_d`），不拿比率相乘 ——
   和 `merchant_scan.js` 同一条纪律：源表那两列是权威值，累乘只用来归因。
   两行分子对不上打 `mismatch`：头条数字照样对（PO 和成功单都取业务单那行），
   但两段的劈法不可全信，卡片上标出来。
2. **缺「支付单支付成功率」行的来源进 `noData`，不当 0。** 当 0 会算出
   「100% 卡在支付前」——**长得像真结论的假结论**，`coverage.js` 踩过同一个坑。
3. **本期没走完时一律不给单量环比**（`partial`，比率环比照给）。周月报选到当前这一期，
   本期才过了几天、上期是整整一周/一个月，单量根本不可比。实测月报 2026-09（第 6 天）
   对 2026-08 会写出「支付中流失 **−92,036 单**」，又大又醒目，能把整张卡的读法带偏。
   和 A2/A3 那条「掉量会虚高」是同一个坑。
4. **支付中流失用「总流失 − 支付前流失」倒推**，不用 `支付单数 − 支付单率分子`。
   分子一致时两者完全相等；不一致时这样算至少保证两段相加 === 总流失 ——
   劈完加起来对不上是最不容易被发现的那种错。

### 配色：不给这两段配新的分类色

页面已经有一套按来源固定的三支色（`--s1/--s2/--s3`）。跑 `dataviz` 的校验时试过再加一对色相：

| 试的色 | 撞谁 | 结果 |
|---|---|---|
| 紫 `#7c5cd6` | 趋势图的蓝 `#2a78d6` | deutan ΔE **0.5** — 硬 FAIL |
| 青 `#0f9a9e` | 趋势图的绿 `#1baf7a` | 正常视觉 ΔE **9.5** — 硬 FAIL |

深色模式的明度带（0.48–0.67）更窄，同色相两档也塞不进去（ΔE 9.8，FAIL）。
所以：**同一支品牌色 + 45° 斜纹**（斜纹是 dataviz 指定的 CVD/打印兜底），
再加段内直标、图例、表格视图 —— 身份从来不只靠颜色。

⚠️ 条的**总长按总流失单量**在各来源之间可比（不是各画各的 100%）——
不然「一家 4056 单流失」和「一家 300 单流失」会画成一样长。
⚠️ 段内直标看它在**整条轨道**里占多宽，不是在本行里占多少：本行只有最宽那行四成时，
「占本行 25%」还是塞不下字，标签会被切掉半截。塞不下就不标，数字在右边那列一个不少。

### 走势看占比，不看单量

`buildPoRateTrend` 出的是「支付前流失占比」的多期序列：单量随大盘涨落，
而这里问的是**结构**有没有在变（流失是不是越来越多地发生在支付之前）。
画图复用趋势图那套 `lineChart` / `wire`（同一个来源、同一支颜色，别再写一份），
缺一期断线不连，没走完的那一期画虚线加 `*`。

## 来源覆盖校验（B8）—— 平时一个字都不出

`coverage.js`。`FLYPAY` 是含全部子场景的全局汇总，作为**来源**不能进分析
（会和子场景重复计数，`ALLOWED_SOURCES` 里没有它是对的），但作为**验算**它是免费的：

```
FLYPAY 的 PO  −  报表里所有子场景的 PO  =  连报表都没单独列行的那部分
```

这是「白名单漏了什么」最硬的检查。`formatDrift()` 那套是字符串比对 ——
上游新增一个场景却沿用旧命名风格时它发现不了，而数字对不上藏不住。

### ⚠️ 缺口是常态，不是「越小越好」

拿两份真实报表实测，缺口**每期都在**：

| 周期 | 缺口范围 |
|---|---|
| 日报 | 0.23% ~ 0.89% |
| 周报 | 0.3% ~ 1.4% |
| 月报 | 0.3% ~ 1.6% |

稳定存在的东西不是异常。用户 2026-09-09 明确说过「0.4% 的数据缺口不算问题」——
第一版我把这个常态当成发现来报，框架就错了。所以这块**平时一个字都不出**，
只在缺口超过 `COVERAGE_GAP_MAX`(5%) 时才在概览提示区说一句。

真正要抓的是**跳变**：2026-09 改版时上游新增了 Element（占大盘 33%），
那种情况缺口会从 0.4% 跳到 33%，一眼看得出来。

### ⚠️ 同样不报「分析覆盖了大盘的 83%」

实测覆盖率 76.9%~83.2%，缺的那 17% 是 FLYLINK 两条线 —— 而白名单是**故意**不纳入它们的
（另一条业务线，漏斗形状不同，`config.js` 里写着理由）。天天在页面上说「你只看了 83%」
是噪声不是信息。那个数只在**报警时**附带说明，帮人判断缺口有多严重。

### ⚠️ 算不出来 ≠ 缺口为 0

某个子场景缺了 PO 行时，加总会偏小、缺口会偏大 —— 那是「读不到数」不是
「上游新增了场景」，报出去就是假警报，而且长得和真警报一模一样。
所以没有 `FLYPAY` 行、只有汇总行没有子场景、`FLYPAY` 为 0 这几种情况一律
`ok:false, alert:false`，并说清为什么。

### 数据从哪来

`ALLOWED_SOURCES` 会把 `FLYPAY` 和 FLYLINK 滤掉，所以默认模式的 `ds.scene` 里没有它们。
`readReport()` 现在**场景维度先全量读一次再自己过滤**（不是读两遍 ——
`loadScene` 每次调用都重解析整个 sheet），额外留一份
`ds.scenePO[周期][期次][来源] = PO单量`。只留这几个数，不留全量行：
全量行在默认模式下是下游不该看见的（会重复计数）。

用例 `tests/coverage.mjs`。

## 基准线三级回退 + 水平信号（B4 + B3）

### 为什么要分池（B4）

`computeBaseline()` 原来只按**指标**分池，三个来源混在一起。Element 和独立站API
的波动尺度差得远，混池算出来的稳健 σ 被小来源的噪声抬高，**大来源的真异常会被那个
抬高的阈值吃掉**。`tests/baseline.mjs` 的 [3] 就是造这个场景：同一个 −2% 的变动，
用本来源池报得出来，用混池被吃掉。

分池之后样本量掉到 1/3，所以**必须有回退**。实测（两份真实报表）：

| 周期 | 分池后每池样本(中位) | ≥8 样本的池子 | 混池 |
|---|---|---|---|
| 日报 | 13 | 36/54 | 33 |
| 周报 |  7 |  **0/54** | 18 |
| 月报 |  5 |  **0/54** | 13 |

```
1. 来源×指标 自己的池   n ≥ POOL_MIN_SRC(8)      basis「基准线·本来源」
2. 全来源混池           n ≥ POOL_MIN_MIXED(5)    basis「基准线·混池」
3. 层级兜底                                       basis「层级兜底」
```

界面上「环比用哪级」那一列写着当前每个指标有几个来源用上了自己的池。

⚠️ **老形状要认。** v2 之前存下来的是 `{指标: 阈值}`（没有 `v`），用户的 localStorage
里就躺着这种。直接按新形状读会得到 undefined，然后**静默**退回层级兜底 ——
界面还照样说着「基准线已启用」。`pickPool()` 里没有 `v` 的一律当混池收，
`tests/baseline.mjs` 的 [5] 钉着。

### 用本机存档算基准线（B11）

`data/inbox/conversion/<日期>.xlsx` 每天都在落盘，以前基准线面板只能人手动多选文件。
现在加了 `GET /api/inbox/dates/conversion`，面板多一个「用本机存档计算」按钮。

**两个坑，都不是管道活**（计划里原来写的是「纯管道活，没有难点」）：

**1 · 报表是滚动窗口，重叠会让 `n` 说谎。** 每份报表带最近 8 期，连着两天的存档重叠
7 期。不去重的话同一个观测被算好几遍 —— 分位数的形状不变（重复值不改变分布），
但 **`n` 会说谎**，而 `n` 正是 `POOL_MIN_SRC` / `LEVEL_MIN_N` 这些门槛在看的东西。

实测把同一份报表喂两遍：水平样本 8 → 16，**池子从 0 个变成 54 个** ——
原本「样本不足、不该出信号」的池子凭空达标，界面上还写着 n=16。
那之后 B3 的水平信号就建在一个假的样本量上。

所以 `collectSamples()` 按 **(期次, 来源, 指标)** 去重（`emptySamples()` 里的 `_seen`）。
环比那侧的 key 要带**两个**日期 —— 不同文件里同一期的「上一期」未必相同（某份报表缺了
中间一期时，相邻对就跨过去了）。

**2 · 取存档要均匀取样，不是取最近 N 份。** 同样因为滚动窗口：取最近 12 份日报
≈ 19 个不同期次，而在全部存档里均匀取 12 份能覆盖上百个。`spreadPick()` 永远含
最新那份，其余等距取，`ARCHIVE_MAX_FILES`(12) 是按「单份 XLSX.read 2.3 秒」定的
—— 12 份 ≈ 30 秒，再多该让人等太久。

界面上把「存档共 N 份 / 取了 M 份 / 去重后最多 X 个期次」都写出来 ——
存档重叠时这三个数差得很远，不写的话人会以为 12 份就只有 12 个样本。
拿真实文件验过：4 份存档（其中 3 份内容相同）→ 去重后 15 个期次，不去重会是 31。

### ⚠️ 混池不是无条件的：水平差太远就不许混

`pickPool()` 的第 2 级（混池）**有前提** —— 这些来源在这个指标上得可比。实测 54 个
「来源×指标」里 8 个差 10pt 以上：

```
67.1pt   来源A · 2. 业务校验通过率      自己 31.85%   混池 98.94%
41.3pt   来源B · 1.2 Paynow点击率     自己 58.70%   混池 100.00%
32.3pt   来源C · 4.1 非3DS网关通过率   自己 38.91%   混池  71.22%
20.4pt   来源C · 4. 网关通过率         自己 56.27%   混池  76.70%
```

对这种拿混池的阈值去卡，报出来的每一条都是误报。所以 `buildBaseline()` 会算一份
`bl.noMix`，`pickPool()` 命中就**跳过混池直接走层级兜底**。判据是
`|本来源水平中位 − 混池水平中位| > MIX_MAX_GAP(10pt)`，
水平样本不足 `MIX_MIN_SAMPLES(3)` 个、判断不了的也不许混 ——
刚上线的来源恰恰最不该用别人的阈值。

⚠️ **判据用绝对水平的差，而混池混的是环比样本** —— 看着不对位，但没有别的办法：
波动尺度要比就得先算出各自的 σ，而算得出 σ 就说明本来源样本够了，根本退不到混池这一级。
水平差几十 pt 的两个来源业务形态本来就不是一回事，拿绝对水平当代理指标是这里唯一能用的判据。

基准线面板最后一列「不许混池」列出每个指标有哪些来源被排除了。

### 水平信号（B3）：环比之外的第二类判据

在此之前**只有环比告警**，指标的绝对水平从来没建过模。于是一整类问题结构性地报不出来。
`level.js` 出两类：

| 信号 | 判据 | 回答的问题 |
|---|---|---|
| ⚠️ 跌破历史下沿 | 本期值跌破该池 P10（摩擦类涨破 P90） | 「今天这个数在历史上算什么位置」 |
| 🌡️ 温水煮青蛙 | 连续 ≥`CREEP_MIN_RUN`(3) 期不高于 P25（摩擦类不低于 P75） | 「是不是一直在慢慢烂」 |

**实测证据**（两份真实报表，每期用它之前的期次建基准 —— 也就是生产口径）：
**20 条只有水平/温水报得出来，环比也报得出来的只有 3 条。** 最有说服力的一条：

```
2026-09-04  独立站API · 4. 网关通过率
    本期 48.96%   历史 P10 49.85%   中位 56.27%     ← 环比只有 −1.33%
```

历史中位 56%，今天 49%，差 7pt —— 而环比一辈子报不出来。
顺带暴露了环比判据的结构性盲区：`4.1 非3DS网关通过率` 掉到 34.98%（中位 40.88%），
环比 −9.59% 也没触发 —— **这个指标本身波动大，基准线算出来的环比阈值必然松**。

### ⛔ 「常年趴在 60%」报不出来 —— 这是**故意**的

B3 那条计划的开头写的是：「一个指标常年趴在 60%、每天纹丝不动，永远不告警 ——
而它可能才是最大的那块肉。」上面这两类信号**解决不了它**：常年 60% 的指标它自己的
历史 P10 也在 60% 附近，永远跌不破；真的纹丝不动的话 `P25 === P50`，
直接被 `hasRoom()` 挡在门外（见下面第 2 条坑）。

唯一能说「60% 太低」的办法是拿一把**外部尺子**，而这里能拿到的外部尺子只有
「别的来源」。**用户 2026-09-09 明确要求：不做跨来源比较。**

实测支持这个决定 —— 54 个「来源×指标」里 **8 个的绝对水平差得没法比，最大差 67pt**。
拿别家的水平去卡这一家，报出来的每一条都是误报，就是下面第 1 条那个混池误报的放大版。

`tests/level.mjs` 的 **[7c]** 钉住这个故意的行为：常年 60% 的来源哪怕同期别家 92%
也不出信号，但**计进 `flat` 报上去**（不是静默丢掉）；而它一旦真的开始往下掉，
自己的分布就有区分度了，照常报得出来 —— 不是把这个来源整个关掉。

⚠️ 以后有人照着计划文档「补上跨来源比较」，[7c] 会挂。**那是提醒，不是 bug。**
真要做，先改那条用例和计划文档。
⚠️ 别和 **B14 待观察商户**的「低于同来源中位数 10pt」搞混：那是**同一个来源内部**
商户之间比，不跨来源，照常在跑。

### 四个踩过的坑（都拿真实报表验过）

**1 · 水平信号不做混池回退。** 环比混池勉强说得过去（各来源的变化幅度量纲相近），
**绝对水平不行**。混池那版第一条报的是：

```
某来源 · 2. 业务校验通过率   本期 29.70%   低于混池 P10 31.88%   混池中位 98.94%
```

那个中位是**另外两个来源**的水平；这个来源那几期就在 30% 上下，在**它自己的**分布里
29.70% 完全正常（自己的中位 31.85%）。所以 `pickLevelPool()` 只认本来源池，
`bl` 里干脆不存 `levelMixed`。

⚠️ **这是「混池会误报」的例子，不是「那个指标有问题」。** 数据截到 2026-09-06；
之后报表结构做了优化，那个来源的 `2. 业务校验通过率` 和 `1.2 Paynow点击率` 已稳定
100%（`1.1 校验1通过率` 待定）。恒 100% 的指标由 `hasRoom()` 挡掉，一条都不会报。

**2 · 分布没有下沉空间的指标不出信号。** 第一版报出来：

```
独立站API · 1.2 Paynow点击率   连续 8 期 ≤ P25(100.00%)   本期 100.00%
```

它是满分。常年 100% 的指标 P25 = P50 = 1.0，「不高于 P25」恒成立。
`hasRoom()` 要求 `p25 < p50`（摩擦类 `p75 > p50`），没有区分度的直接跳过并计入 `flat`。

**3 · ★ 排序和取舍看单量，不看 pt。** 这是 B1/B2 那次的教训又踩了一遍。只按 pt 排时
头几条是 `低 0.06pt` —— 技术上没错，但没人会去处理。现在折成

```
影响单量 = (中位 − 本期值) × 该环节分母 × 下游各环节通过率累乘
```

也就是「**回到自己的历史中位水平能多成多少单**」，按它排、按它筛
（`LEVEL_MIN_ORDERS = 5`）。实测这一步会让排序翻转：

| 指标 | pt 缺口 | 影响单量 |
|---|---|---|
| `4. 网关通过率` | 0.26pt | **+402 单** |
| `4.1 非3DS网关通过率` | 1.89pt | +244 单 |

按 pt 排 `4.1` 在前，按单量排 `4.` 在前。摩擦类和源表没给分子分母的**算不出单量**，
写「—」并排在后面 —— 但**不丢掉**，不能因为标不出价就当它不存在。

**4 ·「没算」和「算了没事」不能长一样。** 结果里带 `noBaseline / checked / noPool /
flat / thin` 五个计数，界面上各有对应文案。没基准线时那块显示的是「去哪开、怎么开」，
不是一片空白 —— 空白会让人以为这块功能坏了，或者干脆注意不到它存在。

### 期次排序：`collectSamples` 也走自然序

原来是裸 `.sort()`。周报期次写成 `2026 W9` / `2026 W37` 时字典序会把 W9 排到 W37
后面，于是「相邻两期」配错对，算出来的环比样本是**跨了几周的变化**。
和 B5 折线那处是同一个 bug，只是这边算出来的是阈值，错了更隐蔽。
`tests/baseline.mjs` 的 [2] 钉着。

## 多维表格：三张表

| 表 | 内容 | 每天行数 |
|---|---|---|
| `scene` | 场景指标（老表，补了 `PO单数 / 进入本环节 / 通过本环节 / 影响单量`）| ~54 |
| `merchant` | 商户明细 —— **只存触发告警的下钻行**（全量是每天 ~1400 行、一年 50 万）| ~42 |
| `watchlist` | 商户名单 —— 掉量 / 新增 / 低于同行 / 刚审核通过，四类合一张用「类型」列区分 | ~40 |

`config.json` 的 `feishu.bitable.tables.<名>`；`scene` 兼容老的 `table_id`。
没配的表**跳过并说清去哪填**，不报错 —— 三张表可以只建一张。
写的时候**串行**：三张共用一个 token，并发容易撞频控，而那个错和字段类型错误长得一样。

⚠️ **列名是人在飞书里手工建的**，代码这边改个字段名不会有任何报错 —— 飞书只是从那天起
那一列全空，没人会发现。`tests/bitable.mjs` 拿三张清单钉着，改列名要三处同时改
（用例、`feishu.js` 的 builder、`README.md` 的建表表格）。

⚠️ 新两张表**直接发数字**（`0.6`），不发 `"60.00%"`。少一道字符串解析就少一类静默出错：
解析不出来的值会被原样写进百分比字段，而飞书报的错和字段类型错误长得一模一样。
老的 `scene` 表还在发字符串，那是历史包袱，服务端 `_parse_field_for_bitable` 兜着。

⚠️ 商户名单表**每条都带齐全部列**（哪怕是空的）。少列的那几条飞书会当成「没这个字段」，
以后按列筛选时那些行会莫名其妙漏掉。

## 源表「环比」列的口子

2026-09 改版把 `场景维度` 的 `环比` 列整个拿掉了，上游说后面会加回来。
它一没，`detect()` 读不到就整行跳过 —— 告警链路整条静默失效。

识别收在 `load.js` 的 **`DOD_ALIASES`** 一处（`环比` / `日环比` / `周环比` / `月环比`，
后三种是业务本来就在用的叫法，见 `config.js` 的 `PERIODS.dod`）。认到哪个都归一成
`o['环比']`，`detect()` / `computeBaseline()` 只认这一个名字。
**列加回来时若换了名字，只改这个数组。**

⚠️ 接回来之前先定口径：`detect()` 把它当**相对环比**用，直接和 `LEVEL_THRESHOLDS` 比。
上游若改发 pt 差值，要在 `DOD_ALIASES` 那里换算 —— 口径错了两级都不报错，只是一直判错。
详见 `后续优化计划.md` 第四轮 A1。

配套：`formatDrift()` 的 `dodColumn:{present,name}`、`detect()` 的 `noBase`、
概览 summary 区分「真平稳」和「一条都没判」。用例 `tests/dod_column.mjs`（`node` 直接跑，
不需要服务也不需要 fixtures）。
