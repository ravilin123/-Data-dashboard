# 口径

交给公司研发的口径说明。读者没读过工作台代码；照这份文档用别的语言重写，再用 `fixtures/golden/` 的黄金用例验收（怎么验收见 `docs/交付说明.md`）。

**每一句都有出处**：口径层代码的模块 / 函数 docstring、`docs/坑.md`（下文的 `§x` 就是那份文档里的条目号，和代码注释里写的 `CLAUDE.md §x` 是同一套号）、`docs/specs/商户流失.md`。每条规则都有黄金用例钉着（各节末尾列了路径）。
参考实现的路径都是本仓库里的相对路径；它们是从工作台 `payment-ops-workbench`（commit `94554cd`）原路径同步来的，本仓库不改。

## 通用规矩（每一节都适用）

| 规矩 | 出处 |
|---|---|
| **算不出来给 `null` + 原因，不给 0。** 缺一天台账是「缺」，画成 0 是深坑；某个子项读不到数时整块 `ok:false`，不能当 0 算出一个长得像真结论的假结论 | `§2.12`，`docs/specs/看板/契约.md` |
| **顺序走数组，不走 dict 键序。** 档位、命中类型、周期、维度的显示顺序都由数组定义；JSON 落盘时键会被按名排序，所以键序不承载任何信息 | `§2.18.5` |
| **截断必须自报。** 表被砍了要带 `truncated` / `below` 这种「被挡掉多少」的数 | `§2.16.5`，`churn/daily.py`，`churn/trade.py: drill` |
| **配置里的数字：`null` / 空串 / 垃圾值回默认，`0` 要留住。** `.get(k, 默认)` 挡不住 `null`，`or 默认` 会吃掉有意义的 `0`（`recover_ratio=0`、`gateway_incident_top_n=0`=不限、`daily_min_tpv=0`=不设门槛） | `§2.18.98`，`churn/config.py: _int/_float` |
| **用户ID 是 19 位整数，全程当文本。** 超过 2^53，经过一次浮点就丢精度，而它是所有对账的键 | `churn/adapters.py`，`order_monitor/excel.py: clean_uid` |
| **空格子是空串，不是字面量 `"nan"`。** 负责人（直签人 / 所属BD）空的显示为「未分配BD」 | `§2.18.96`，`names.py` |

术语（沿用 `docs/specs/商户流失.md` 开头那段）：**站点** = 用户ID + 站点，流失和交易概览的判定单位；**台账** = 每天一份的站点级记录（`{日期: [站点行]}`）；**命中** = 状态机某天产生的一条事件；**落点** = 一行数据最后去了哪（通知+表 / 仅表 / 丢弃）；**期次** = 报表自带的周 / 月标签，如 `2026 W37 (2026-09-04~2026-09-10)`。

### 台账里「站点行」的公共字段

所有 `churn/*` 的口径吃的都是这一种行（`churn/adapters.py: PUBLIC_FIELDS`；进台账后去掉 `报表类型` / `统计周期` 两列，`统计周期` 变成外层的日期键）：

| 列 | 类型 | 允许空 | 含义 / 上游列名 |
|---|---|---|---|
| `用户ID` | 文本（19 位数字） | 状态机、周报里空则整行不算；大盘不过滤 | 商户的用户 ID。上游列 `用户ID` |
| `站点` | 文本 | 同上 | 站点域名。上游列 `站点` |
| `商户名称` | 文本 | 允许 | 上游列 `商户名称` |
| `直签人` | 文本 | 允许（空 → 「未分配BD」）| 上游列 `直签人`；可能是人名、19 位代理商 ID、或空（实测 35% / 39% / 26%，spec 「核过的数字」） |
| `代理商ID` | 文本 | 允许 | 上游列 `代理商用户ID` |
| `代理商名称` | 文本 | 允许 | 上游列 `代理商名称` |
| `接入模式` | 文本 | 允许（空 → 「—」）| 上游列 `接入模式` |
| `交易金额` | 浮点，美元 | 空 → 0.0 | 上游列 `交易金额（美元）` |
| `交易笔数` | 整数 | 空 → 0 | 上游列 `交易笔数`（上游是 `1288.0` 这种浮点，四舍五入成整数） |

上游报表：FlyPay 独立站收单统计表第一张 sheet；只有 `报表类型 == 日报` 且 `统计周期` 是 `YYYY-MM-DD` 的行进日台账，周报行单独留一本「周台账」（`churn/ledger.py: split_daily / split_weekly`）。同一天在多份文件里出现时，**业务日期更晚的那份整个盖住**（`churn/ledger.py` 文件头）。多站点商户同一天几行就留几行，**永不合并**（spec「台账」段；tpv-sync 合并过，少了 5.2% 的 TPV）。

网关台账行（`churn/adapters.py: GATEWAY_FIELDS`，来自「站外_网关TPV统计报表」的 `网关_商户维度` sheet，按名字认 sheet，`§2.20`）：`网关`（上游 `网关`）、`用户ID`、`交易金额`（上游 `交易金额_美元`）、`交易笔数`；日期键来自上游 `统计日期`。**没有站点列** —— 这决定了网关标签是商户级的（第 4 节）。

## 1 · 名字清洗与档位

**定义**：负责人格子（`直签人` / `所属BD`）怎么变成一个能显示、能分组、能路由的名字；以及怎么判断「直签人写的其实是代理商的 ID」。

**输入**：一个格子的原始值，任意类型（`None`、浮点 NaN、字符串、数字）。

**参数**：无。常量 `UNASSIGNED = "未分配BD"`；`MODES = ("both", "group", "dm", "silent")` 是推送四档的唯一定义（`§2.18.95`，四档在出单监控和商户流失两处一字不差）。

**算法要点**（`names.py: owner_name`）：
1. `None` → 「未分配BD」。
2. 浮点且是 NaN → 「未分配BD」。
3. 其余转成字符串并去掉首尾空白；空串、或小写后等于 `nan` / `nat` / `none` / `null` 之一 → 「未分配BD」。
4. 否则返回去掉空白后的字符串。数字 `0` 会变成字符串 `"0"`，不是「未分配BD」（黄金用例里钉着）。

`names.py: is_agent_id(name)`：**纯数字且长度 ≥ 15** 才算代理商 ID。`"12345678901234"`（14 位）不算，`"12345abc"` 不算。

显示成「代理商：xxx」（`churn/overview.py: owner_label`、`churn/broadcast.py: owner_note`）：先 `owner_name`，若结果是 15 位以上纯数字 → `"代理商：" + 代理商名称`，代理商名称也空则接那串 ID 本身；否则就是那个名字。

**边界与刻意的决定**：
- 这个函数是「未分配BD」**唯一的出处**，群消息、私聊分组、台账、商户流失的直签人都走它；只判 `if not bd` 挡不住 `"nan"`（`§2.18.96`）。
- 直签人是代理商 ID 或空时，推送路由到配置里的兜底人；配了 `agent_owner`（代理商ID → BD 姓名）就按它换名（`churn/broadcast.py: owner_of`，spec「推送」段）。
- `overview.owner_label` 和 `broadcast.owner_note` 里那句「15 位以上纯数字」是各自内联写的，没有调用 `is_agent_id`，三处逻辑目前一致（读代码核过）。

**输出形状**：`owner_name` → 字符串；`is_agent_id` → 布尔。黄金用例的 expected 是对输入数组逐个映射后的数组。

**黄金用例**：`fixtures/golden/names/owner_name_空和nan一律未分配BD/`、`fixtures/golden/names/is_agent_id_15位以上纯数字/`。

**工作台实现**：`names.py: owner_name()`、`is_agent_id()`；显示层 `churn/overview.py: owner_label()`。别名：`order_monitor/classify.py: clean_bd_name`（同一个函数对象）。

## 2 · 交易大盘

**定义**：把日台账汇成三样：每天一个点的趋势（金额 / 笔数 / 有交易的站点数）、当日 KPI（环比昨日 + 对前 7 日均值）、当日构成（按接入模式 / 按直签人）和 Top 商户排名（`churn/overview.py` 文件头）。

**输入**：`days = {日期: [站点行]}`（公共字段见上）；`date`（当日，`YYYY-MM-DD`）。**日期键不存在 = 那天缺台账；键存在但是空数组 = 那天有台账、全为 0**，两者不同。大盘不过滤 `用户ID` / `站点` 为空的行（状态机会过滤，见第 4 节）。

**参数**（`build` 签名 + 模块常量）：

| 参数 | 默认 | 含义 |
|---|---|---|
| `n_days` | 30 | 趋势看几天（含当日） |
| `top_n` | 10（`TOP_N`） | 排名前几名 |
| `MAX_GROUPS` | 6 | 构成里最多几类，多的折进「其他」 |
| `AVG_WINDOW` | 7 | KPI 里和「前几日均值」比 |

**算法要点**：
1. **趋势 `series`**：取以 `date` 结尾的 `n_days` 个日期，升序。某天键不存在 → `{ok:false, tpv:null, orders:null, sites:null}`；否则 `tpv` = 该天所有行 `交易金额` 之和（保留 2 位小数），`orders` = `交易笔数` 之和，`sites` = **笔数 > 0** 的 (用户ID, 站点) 去重个数。`gap` = 缺的日期列表。
2. **KPI**（对 `tpv` / `orders` / `sites` 各算一份）：`value` = 当日值（缺 → `null`）；`prev` = 前一天的值（缺 → `null`）；`dod` = `value / prev − 1`（保留 6 位），**只在 `value` 非空且 `prev` 非空且非 0 时算**，否则 `null`；`avg7` = 趋势序列里当日**之前**、`ok` 的天里最近至多 7 天的均值（保留 2 位），**按有数的天数除，不按 7 硬除**；`avg7_days` = 参与均值的天数；`vs_avg7` = `value / avg7 − 1`（`avg7` 空或 0 → `null`）。
3. **构成 `by`**（只在当日有台账时算，否则 `{}`）：`接入模式`（去空白，空 → 「—」）、`直签人`（`owner_label`，见第 1 节）。分组内 `tpv`（2 位）、`orders`、`sites`（只数笔数 > 0 的站点，和头部那个「有交易的站点」同一把尺子）；按 `tpv` 降序、同值按名字升序；超过 6 类时保留前 6 类，其余折成一条 `{"name":"其他","n":折了几类,...}`；`share` = 该组 `tpv` ÷ 当日总金额（保留 6 位），总金额为 0 → 0。
4. **排名 `top`**：按 `用户ID` 把当日多站点**合并成商户**，`商户名称` / `直签人` 取该商户第一行（直签人经 `owner_label`），`站点数` = 站点去重数；按 `tpv` 降序、同值按 `用户ID` 升序取前 `top_n`；`share` 同上；`prev` = 前一天同一商户的 `tpv`（2 位），前一天没这家或为 0 → `null`；`dod` = `tpv / prev − 1`（6 位），`prev` 为 `null` 时 → `null`。
5. `ok` = 台账里至少有一天；台账一天都没有或当日缺时另带 `reason`。

**边界与刻意的决定**：
- 缺天 `ok:false`、值 `null`，趋势图在那一点**断线**；前 7 日均值按有数的天数除（`§2.12`，`churn/overview.py` 文件头）。
- **新出现的商户环比是 `null`，不是 +100%**（`top_merchants` docstring；`tests/golden.py` [3] 钉着）。前一天为 0 同样 `null`。
- 超过 6 类折进「其他」，不生成第 7 种颜色（`churn/overview.py` 文件头）。
- 排名的单位是**商户**（站点合起来）；流失页和交易概览下钻的单位是**站点**。两个数摆一起对不上是正常的。
- 「有交易的站点」只数笔数 > 0 的行（`_day_totals` / `group_by` 注释）。

**输出形状**：`{ok, date, days, series:[{date, ok, tpv, orders, sites}], gap:[日期], kpi:{tpv|orders|sites: {value, prev, dod, avg7, avg7_days, vs_avg7}}, by:{接入模式:[{name, tpv, orders, sites, share(, n)}], 直签人:[…]}, top:[{用户ID, 商户名称, 直签人, tpv, orders, 站点数, share, prev, dod}], reason?}`。

**黄金用例**：交易量群消息文本 `fixtures/golden/churn_trade_msg/有数就有整条消息/`、`当天一个数都没有是空串/`（`trade_msg.group_text(build(days, date), settings)`，空串 = 调用方记「没跑」）；大盘 `fixtures/golden/churn_overview/新商户环比是null不是加100/`、`缺一天序列里是ok_false值null/`、`当天没台账kpi全null但更早的天还在/`、`直签人是19位代理商ID显示成代理商/`。

**工作台实现**：`churn/overview.py: build()`，内部 `_day_totals()`、`_kpi()`、`group_by()`、`top_merchants()`、`owner_label()`。

## 3 · 交易周期分桶（日 / 周 / 月）

**定义**：交易概览页的算数：把日台账按日 / 周 / 月分桶，每期一个点，加当期构成、排名、和报表周行的校验，以及站点级下钻。构成和排名**复用第 2 节**的 `group_by` / `top_merchants`，这里只多做「分桶」一件事（`churn/trade.py` 文件头）。

**输入**：`days`（同第 2 节）；`date`；可选 `weeks` = 周台账列表，每项 `{期次, start, end, complete, source_date, rows:[站点行]}`（`churn/ledger.py: split_weekly / merge_week`）。

**参数**（`build` 签名）：

| 参数 | 默认 | 含义 |
|---|---|---|
| `period` | `"日"` | `日` / `周` / `月`，不认识回 `日`；顺序 `PERIODS = ["日","周","月"]` |
| `n` | 12 | 往前几期（含当期） |
| `metric` | `"tpv"` | `tpv` / `orders`，决定构成和排名**排序和占比**按哪个 |
| `top_n` | 10 | 排名前几 |
| `anchor` | `None` | **周从星期几开始**，0=周一 … 4=周五 … 6=周日。`None` 时从 `weeks` 里每期的起始日投票（出现最多的那个；票数并列取更小的星期），一期都没有 → `WEEK_ANCHOR = 4`（周五） |
| `weeks` | `None` | 周台账；`None` 时会去读本机台账目录（黄金用例一律显式传 `[]`） |

⚠ **`anchor` 必须做成显式参数**（`docs/specs/看板/计划.md` Q25）：工作台的周是**周五 → 周四**（报表定的），公司看板是周日起；同一批数两个锚点分出的周不一样，黄金用例两条各钉一个。

**算法要点**：
1. **一天属于哪一期**（`bucket_of`）：
   - 周：`start = date − ((weekday(date) − anchor) mod 7)`，`end = start + 6`；`key = end`；`label = "{ISO年} W{ISO周:02d}（MM-DD~MM-DD）"`，**ISO 年 / 周号按 `end` 那天算**。
   - 月：`start` = 当月 1 日，`end` = 当月最后一天，`key = end`，`label = "YYYY-MM"`。
   - 日：`key = label = start = end = date`。
2. **往前 n 期**（`periods_back`）：从 `date` 所在期往前逐期取，直到凑够 `n` 期，按 `key`（结束日）**升序**。
3. **换成报表原话**（`relabel`，只对周）：`weeks` 里有 `end` 相同的一期 → `label` 换成它的 `期次` 原文，`from_report: true`；否则保留自己拼的，`from_report: false`。
4. **每期一个点**（`series`）：取这期 `start..end` 每一天，键不存在的记进 `gap`；**整期一天都没有** → `ok:false`、三个值 `null`、`days: 0`；否则 `ok:true`、值同第 2 节 `_day_totals`、`days = span − len(gap)`、`span` = 这期几天。⚠ 当期还没走到的日子（未来）也算在 `gap` 里，不区分「未来」和「缺」。
5. `current` = 最后一期，`prev` = 倒数第二期；`rows` = 当期全部行，`prev_rows` = 上期全部行；`total` = 当期 `交易金额` 之和。
6. **构成 `by`**（当期有行才算）：`接入模式`、`直签人`（同第 2 节）、`代理商`（`代理商名称` 去空白，空 → 「直签」）、`商户`（`商户名称`，空 → 「—」）。都走 `group_by(rows, key_fn, total, metric)`：`metric = orders` 时排序按笔数、`share` 的分母也换成笔数之和（折「其他」也按笔数重折）——**两个指标不能只换个分母**（`group_by` docstring）。
7. **排名 `top`** = `top_merchants(rows, prev_rows, total, top_n, metric)`；`prev` / `dod` 是**和上一期比**。
8. **校验 `check`**：`weeks` 里 `complete` 且 `end` 等于当期 `end` 的那一期 → `报表` = 它的行金额之和，`台账` = 当期算出来的 `tpv`，`差 = 台账 − 报表`，`同 = |差| < max(1.0, 报表 × 0.001)`。没有对得上的周或当期 `ok:false` → `null`。**报表周行只做校验，不做数据源**（`check_against_report` docstring）。
9. `ok` = 台账非空且当期有行；否则 `reason`。
10. **下钻 `drill(days, date, period, filters, metric, limit=200, anchor)`**：当期站点级明细（不合并），筛选维度只有 `DRILL_KEYS = ["接入模式","直签人","代理商","商户","kw"]` 一处（`§2.18.7`）；多维之间是「与」；`kw` 不分大小写匹配商户名称 / 站点 / 用户ID；每个站点 `tpv`、`orders`、`days`（笔数 > 0 的天数）；按 `metric` 降序、同值按 key；超过 `limit` 的切掉并在 `truncated: {n, tpv}` 里自报（`§2.16.5`）。`options()` 给每个维度的取值和出现次数（降序）。

**边界与刻意的决定**：
- 周界**必须用报表自己的**（周五 → 周四），从周台账的期次标签里读，读不到才回落到周五；自己按 ISO 周切的话数和老板手上的报表永远对不上而且不报错（`§2.17.7`）。
- **周号按结束日算，不是起始日**：09-04(五)~09-10(四) 报表叫 W37，按起始日算是 W36，整体差一周，图上看不出来（`§2.17.7`，`bucket_of` 注释）。
- 期次走**自然序**（按结束日），不是 label 字面序：`2026 W9` 字面上排在 `2026 W37` 后面（`§2.9` `§2.17.7`）。⚠ 测排序别拿自己拼的补零 label（字面序碰巧等于自然序），要造 `2026 W9` vs `2026 W37` 这种不补零的期次（`§2.17.7`）。
- 一期缺几天**要报出来**，不许闷头加：少三天的一周和完整的一周画在同一条线上，看着就是「那周掉了」（`§2.12`，`series` docstring）。
- 按笔数看时排序和占比都换（`group_by` docstring）。

**输出形状**：`{ok, date, period, metric, n, week_anchor, current:{key,label,start,end(,from_report), ok, tpv, orders, sites, gap, days, span}, series:[同 current], gap:[当期缺的日期], by:{接入模式, 直签人, 代理商, 商户: [{name, tpv, orders, sites, share(, n)}]}, top:[同第 2 节], check: null | {期次, 报表, 台账, 差, 同}, reason?}`。`drill` 的形状：`{ok, period, label, start, end, gap, metric, filters, total:{tpv, orders, sites}, rows:[{key, 用户ID, 站点, 商户名称, 直签人, 代理商, 接入模式, tpv, orders, days}], truncated: null | {n, tpv}}`。

## 4 · 商户流失状态机

**定义**：纯函数：吃台账若干天 + 网关台账 + 昨日状态 + 配置，吐今天每个**站点**的状态和今天产生的**命中**（沉默跃迁 / 掉量 / 恢复 / 掉量关闭），外加通道异常。单位是站点（用户ID + 站点），不是商户（`churn/assess.py` 文件头，用户 2026-09-15 定的）。

**输入**：
- `days = {日期: [站点行]}`：**读进来的全部天**，不只窗口内 30 天（冷启动时沉默 31~90 天的站点只出现在窗口之外，`assess` 内注释）。**只留 `用户ID` 和 `站点` 都非空的行**；同一天同一键出现多行时**后一行覆盖前一行**（`_index` 用 dict 按键存；黄金用例 `churn_assess/同一天同一站点两行取后一行/` 钉着）。上游报表 46 天实测没出现过重复行；真出现了就是这条规则，不另猜。
- `today`：`YYYY-MM-DD`。
- `prev`：昨天这个函数的输出（用其中的 `sites`），冷启动传 `null`。
- `cfg`：整份 `config.json` 或只有 `churn` 那段的 dict，经 `churn/config.py: settings()` 规整。
- `gateway = {日期: [网关行]}`，可不传；网关行只用 `用户ID`、`网关`、`交易笔数`。

**参数**（`churn/config.py: DEFAULTS` + `assess.py` 常量）：

| 参数 | 默认 | 含义 |
|---|---|---|
| `top_n` | 30 | 最近 `window_days` 天滚动 TPV 排前 N 的站点才有**推送资格** |
| `silence_days` | `[2, 7, 30]` | 沉默满几天各跃迁一次；配置可写 `"2,7,30"`，去重排序，垃圾丢掉 |
| `drop_push` | −0.70 | 日环比 ≤ 这个 → 「掉量·推」 |
| `drop_page` | −0.50 | 日环比 ≤ 这个 → 「掉量·页面」 |
| `recover_ratio` | 0.8 | 掉量开了之后回到掉量前水平的这个比例 → 「掉量关闭」 |
| `sporadic_max_days` | 10 | 窗口里活跃 ≤ 这么多天 → 零星型 |
| `window_days` | 30 | 滚动窗口 |
| `gateway_incident_min` | 3 | 同网关当天 ≥ 这么多**家**一起掉 → 通道异常；配 0 按 1 算 |
| `gateway_incident_top_n` | 50 | 通道异常只数排名前这么多的站点；**0 = 不限** |
| `DROP_WINDOW` | 2（常量） | 掉量开了之后看几天 |
| `PRUNE_AFTER` | 90（常量） | 沉默超过这么多天的站点不再跟踪 |
| `HIT_ORDER` | `["沉默30","沉默7","沉默2","掉量·推","掉量·页面","恢复","掉量关闭"]` | 命中类型的顺序（走数组） |

其他配置项（`mode` / `webhook_url` / `boss_emails` / `fallback_email` / `agent_owner` / `bitable` / `daily_min_tpv` / `daily_top_n`）不参与本节的算数，只在 `ok:false` 的输出里原样带出。

**算法要点**（一次调用 = 算一天）：
1. `today` 不在 `days` 里 → `{ok:false, reason:"<today> 没有台账，这天算不了", gap:[], sites:{}, hits:[], counts:{}, settings:<全量规整配置>}`，到此为止。
2. `window` = 以 `today` 结尾的 `window_days` 个日期；`gap` = 其中在 `days` 里没有键的日期。
3. 候选站点 = 昨日状态里的全部站点 ∪ 读进来的所有天里出现过的全部键。
4. 对每个站点（按键升序）：
   - `latest_row` = 最近一天（≤ today）的那行，用来取商户名称、直签人等 7 个字段（`SITE_FIELDS`），取不到就沿用昨日状态里的。
   - `last_active` = 最近一个 **`交易笔数 > 0`** 的日子；本次输入里一天都没有 → 用昨日状态的 `last_active`；还没有 → 这个站点从没出过单，**跳过**。
   - `silent_days = today − last_active`（自然日）；> `PRUNE_AFTER`(90) → 跳过，不进 `sites`。
   - **滚动值的窗口以 `last_active` 为终点**：`last_active == today` 用 `window`，否则用以 `last_active` 结尾的 `window_days` 天。`tpv30` = 窗口内该站点 `交易金额` 之和（2 位）；`active30` = 窗口内笔数 > 0 的天数；`tpv_asof` = 窗口终点。
   - `active_today` = 今天有这行且笔数 > 0；`uncertain` = `gap` 里有任何一天晚于 `last_active`。
   - **沉默**：`active_today` 时，昨日档位 > 0 → 命中「恢复」、`recovered_on = today`；档位归 0。否则若 **不** `uncertain`：`top` = `silence_days` 里 ≤ `silent_days` 的最大档（没有则 0）；`top` > 昨日档位 → 档位 = `top`、命中 `"沉默{top}"`、`recovered_on` 清空。（一档只跃迁一次；冷启动沉默 8 天直接命中「沉默7」，不补「沉默2」；`uncertain` 时不跃迁、不命中。）
   - **掉量**：先看昨日状态里有没有开着的 `drop`。有：`age = today − opened`；`active_today` 且今天金额 ≥ `recover_ratio × base` → 命中「掉量关闭」、`drop` 清空；否则 `age ≥ DROP_WINDOW`(2) → `drop` 静默清空（**过期，不算关闭，不命中**）。没有开着的（含刚过期的）且 `active_today` 且今天没命中「掉量关闭」：昨天有这行且笔数 > 0 且金额 > 0 → `ratio = 今天金额 / 昨天金额 − 1`；≤ `drop_push` → 「掉量·推」，否则 ≤ `drop_page` → 「掉量·页面」；命中并记 `drop = {level, opened: today, base: 昨天金额, ratio(6 位)}`。开着的期间不再开第二个。今天没单**不算掉量**（那是沉默那条线的事）。
   - 网关标签 `gw`（按 `用户ID`，**每个站点都标**）：`gateway` 里**没有 `today` 这个键** → 「网关数据缺」；有键（哪怕是空数组）且今天该用户ID 有任何一行笔数 > 0 → 「其他通道仍有交易」，否则 「全网关停止」。
   - `sporadic = active30 ≤ sporadic_max_days`。
5. **排名**：`tpv30 > 0` 的站点按 `tpv30` 降序、同值按键升序，`rank` 从 1 起；`eligible = rank ≤ top_n`。`tpv30 == 0` 的 `rank: null`、`eligible: false`。
6. **命中列表**：每个站点今天的每条命中一项，带该站点的全部字段；`drop` 字段只在类型是「掉量·推 / 掉量·页面」时带，否则 `null`。排序：有资格的在前 → `tpv30` 降序 → 键升序 → `HIT_ORDER`。
7. **通道异常**（`incidents`）：只看类型以「沉默」开头或是「掉量·推 / 掉量·页面」的命中（恢复 / 掉量关闭不算）；`gateway_incident_top_n > 0` 时只看 `rank ≤` 它的站点。每个商户归到**它最近一次在网关台账里有交易（笔数 > 0）那天**用的网关（从今天往回找，含今天；`gateway_view.home`）。按网关聚合：`uids`（去重的用户ID）、`merchants = len(uids)`、`sites`（条数）、`types`（各类型条数）；`merchants ≥ gateway_incident_min` 的网关才算出事；按 `merchants` 降序、网关名升序。然后给每条命中打 `incident = [它的网关里出了事的那些]`，站点上同步。
8. `counts` = 命中按类型计数；`eligible_n` = 有资格的命中数；`gateway = {has_today, latest: 最近一天 ≤ today 的网关日期或 null, merchants: 今天有交易的用户ID 数}`；`settings` 只带 8 个算数参数。

幂等：同样的输入两次结果相同；不改输入（文件头）。

**边界与刻意的决定**：
- **单位是站点**，一家七个站点是七条状态；但通道异常**数的是家不是条**，一家 7 站点一起沉默是 1 家（`incidents` docstring；黄金用例 `通道异常_2家乘7站点14条仍不报`）。
- **缺口不跃迁**：缺口横在「最后有交易日 → 今天」中间的站点标 `uncertain`，天数够了也不猜；今天自己没台账 → `ok:false`。「算不出来不能当算出来了」（`§2.12`，文件头「缺口」）。
- **网关标签三种，缺数据是独立的一种**，不许并进「全网关停止」——后者会让 BD 直接去催商户（`§2.12`，`gateway_label` docstring；黄金用例 `不传网关一律网关数据缺`）。⚠ 「今天有键但空数组」按「有数据」处理，全部标「全网关停止」（`gateway_view: has_today = today in gw_days`；黄金用例 `通道异常数的是家不是条` 就是这样构造的）。
- 网关标签是**商户级**的：网关报表没有站点列，「其他通道」包含这家商户自己别的站点（文件头「网关」）。spec 里写「沉默站点带一个标签」，代码是**每个站点都带**（含活跃的），页面只在沉默名单上显示 —— 以代码为准。
- **滚动窗口以最后有交易日为终点**，否则沉默满 30 天的站点 `tpv30` 必然是 0、排名垫底、最高档永远拿不到推送资格；`active30` 同理，否则大站点会被误标零星型（文件头「滚动值」）。页面上 `tpv_asof ≠ today` 时要标出来。
- 推送资格在命中当天按当天排名算，**不回溯**（spec「流失状态机」）。
- 「掉量·页面」、「恢复」、「掉量关闭」**只在页面**，不推送（`churn/broadcast.py` 文件头）；推的只有前 N 的沉默跃迁 + 「掉量·推」（`broadcast.pushable`）。
- 日环比在台账上现算，报表自带的环比列只做校验（spec）。
- 沉默超过 90 天不再跟踪（最高档早就推过了，`PRUNE_AFTER` 注释）。
- 周环比 ≤ −50% 不在这里，只进周报（第 6 节）。

**输出形状**（`ok:true`）：
```
{ok:true, date, window:[日期], gap:[日期],
 sites:{ "<用户ID>|<站点>": {用户ID, 站点, 商户名称, 直签人, 代理商ID, 代理商名称, 接入模式, key,
          gw, incident:[网关], last_active, silent_days, silence_level, recovered_on,
          drop: null | {level, opened, base, ratio}, tpv30, tpv_asof, active30, uncertain,
          sporadic, rank, eligible} },
 hits:[{key, type, eligible, tpv30, rank, tpv_asof, active30, uncertain, recovered_on, gw, incident,
        silent_days, sporadic, last_active, drop, + 7 个站点字段}],
 counts:{类型: 条数}, eligible_n, incidents:[{网关, uids, merchants, sites, types}],
 gateway:{has_today, latest, merchants},
 settings:{top_n, silence_days, drop_push, drop_page, sporadic_max_days, window_days,
           gateway_incident_min, gateway_incident_top_n}}
```

**黄金用例**：`fixtures/golden/churn_assess/` 下 9 条：`沉默不到2天不算命中`、`沉默2天跃迁一次`、`掉八成是掉量推送档`、`台账缺一天要报gap不当0`、`今天没台账算不了ok_false`、`网关标签三种`、`不传网关一律网关数据缺`、`通道异常数的是家不是条_正好3家报`、`通道异常_2家乘7站点14条仍不报`。播报 `fixtures/golden/churn_broadcast/只推前N的沉默跃迁和掉量推_群和私聊分组/`、`通道异常单独一行_缺数据一个字不出/`（`pushable` / `group_text` / `group_for_dm` + `bd_text`）；多日连跑（每天喂前一天的状态，输出 `{dates, hits:{日期:[类型]}, states:{日期:状态}}`）：`fixtures/golden/churn_assess_chain/一档只跃迁一次/`、`恢复归零并清掉已恢复标记/`、`掉量关闭_两天内回到八成/`、`掉量过期_两天没回不命中静默清掉/`、`缺口横在中间不跃迁/`。

## 5 · 流失日报汇总

**定义**：把某一天的状态汇成三行 + 前几家：新沉默（多少钱 · 几家 / 几个站点 · 各档几个站点）、掉量（少了多少钱）、通道异常；群里发这份**汇总**，BD 私聊照旧发**逐条**（`churn/daily.py` 文件头；`§2.21.4`）。

**输入**：`state` = 第 4 节 `assess()` 的输出；`settings` = **扁平的** dict（`{"daily_min_tpv": …, "daily_top_n": …}`，即 `churn/config.py: settings()` 规整后的形状；⚠ 不是 `{"churn": {...}}` 那层，见下面黄金用例的说明）。

**参数**：

| 参数 | 默认 | 含义 |
|---|---|---|
| `daily_min_tpv` | 5000 | 30 天 TPV **≤** 这条线的命中不进汇总（进 `below` 自报）；**`0` = 不设门槛，是有意义的一档**，判 `is None` 不判 `or` |
| `daily_top_n` | 5 | 底下列前几家 |

**算法要点**：
1. `state` 为空或没有 `hits` → `{ok:false, reason:"今天没跑过，算不出来"}`，**不写「0 家」**。
2. 只关心三档：类型以「沉默」开头、或是「掉量·推 / 掉量·页面」。恢复 / 掉量关闭不进汇总。**不看 `eligible`**（扫全部命中）。
3. `floor` = 门槛；`tpv30 > floor` 的进 `big`，`≤ floor` 的进 `small`（门槛 0 时 `tpv30 == 0` 的仍在 `small`）。
4. `silence`：`big` 里沉默类的 `tpv30` 之和（「这家有多大」，它已经不出单了）、站点数、按 `用户ID` 去重的家数、`tiers` = 各类型条数（`{"沉默2": n, …}`）。
5. `drop`：`big` 里掉量类的 **`drop.base` 之和**（前一日的量 = 这次少掉的钱，不是 30 天 TPV）、站点数、家数。
6. `below = {hits: small 条数, tpv: small 的 tpv30 之和}` —— 被挡掉的自报。
7. `incidents` 原样带出。
8. `top` = `big` 按 `用户ID` 合成商户（`tpv` = 各站点 `tpv30` 之和，`sites` 条数，`rows` 原命中），按 `tpv` 降序、`用户ID` 升序，取前 `daily_top_n`。
9. 正文 `text()`：三行分开写；沉默一行的档位分解只有多档时才带括号，单位写「个站点」不写「家」；掉量一行明写「还在出单，没算进上面」；有挡掉的才写「另有 N 条在 $X 以下，没列」；**一条都不该报时返回空串**，调用方据此不发。

**边界与刻意的决定**：
- 门槛看的是**这家商户有多大**（30 天 TPV），不是这次掉了多少：实测 2026-08-22 那天 36 条命中过 $5,000 的只有 10 条，但那 10 条占 95% 的金额（`§2.21.4`，文件头）。
- **沉默和掉量不许相加**：一个是「走了」一个是「还在出单但少了」（文件头）。
- 「家」和「个站点」是两个单位，不许混（`§2.21.4`）。
- 被门槛挡掉的要自报（`§2.16.5`，`§2.21.4`）。
- `§2.21.4` 说的「两道闸」（2026-09-18 对着工作台 `churn/job.py: _push()` 核过）：**本函数只有 `daily_min_tpv` 一道闸，不看 `eligible`**；`top_n` 那道闸在发送编排里 —— 编排先算 `broadcast.pushable(state)`（前 `top_n` 的沉默跃迁 + 「掉量·推」），**一条可推送的都没有时整个不发**（群汇总也不发）；有的话群里发本函数的汇总（全部命中过 `daily_min_tpv`），BD 私聊发 `pushable` 那批逐条。重写时若要复现「群里什么时候发」，必须把这道前置条件也搬过去。

**输出形状**：`{ok:true, date, floor, silence:{tpv, sites, merchants, tiers}, drop:{tpv, sites, merchants}, below:{hits, tpv}, incidents:[…], top:[{用户ID, 商户名称, 直签人, 代理商名称, tpv, sites, rows:[命中]}]}`；或 `{ok:false, reason}`。

**黄金用例**：`fixtures/golden/churn_daily/门槛看商户多大不看掉了多少/`、`门槛0是不设门槛不被or吃掉/`；正文 `churn_daily_text/掉量单独一行_明写还在出单没算进上面/`、`一条都不该报时是空串/`。
⚠ 这两条的 `settings.json` 是**扁平**的（`{"daily_min_tpv": 0, "daily_top_n": 5}`），不是 `{"churn": {...}}` —— `summary()` 读扁平 dict。第一版写成了带段的形状，两条 expected 一模一样、`floor` 都是 5000（2026-09-18 抓到并修了）；`tests/golden.py` 现在钉着「门槛 5000 和门槛 0 的两条 expected 必须不同、`floor` 分别是 5000 / 0」。

**工作台实现**：`churn/daily.py: summary()`、`min_tpv()`、`by_merchant()`、`text()`、`tiers_items()`。逐条私聊：`churn/broadcast.py: bd_text()`、`group_for_dm()`。

## 6 · 老板周报

**定义**：每周一给老板的三行摘要：**头条** = 上一个完整周活跃、这一周一笔没有的站点，其上一周 TPV 之和（和报表「流失率」同口径）；**在途风险** = 这一周新进沉默满 7 天（或更高档）的站点各自的 30 天 TPV 之和（下周还会掉多少）；**掉量** = 周环比 ≤ `drop_page` 的站点单列。三行刻意分开，不许合并成一个数（`churn/weekly.py` 文件头）。

**输入**：
- `ws`：周台账列表，升序；每项 `{期次, start, end, complete, rows:[站点行]}`；**只用 `complete` 的**（报表业务日期过了周末日才算走完，`churn/ledger.py: merge_week`）。
- `states`：这一周窗口内每天的状态（第 4 节输出）列表；**`None` = 窗口算不出来**，`[]` = 那几天真的没状态，两回事。
- `settings`：扁平 dict，只用 `drop_page`（默认 −0.50）。
- `follow`：`{用户ID|站点: {跟进人, 状态}}`，从多维表格回读（人手填）。
- `date`：运行日（只原样带出，**不进标题**）。

**参数**：`RISK_TIER = 7`（在途风险数沉默满几天）、`TOP_N = 5`（前几家）、`drop_page`（周掉量线）、`ACTIVE_STATES = ("跟进中", "已挽回", "放弃")`（「真有人在跟」的状态）。

**算法要点**：
1. 过滤出 `complete` 的周；不足 2 个 → `{ok:false, date, reason}`。`prev`、`cur` = 最后两个。
2. 一周的行按 `用户ID|站点` 归并（两者都非空才算；同键相加）。「有交易」= 笔数 > 0 **或** 金额 > 0（报表里见过笔数 0 金额非 0 的退款行，`_live` docstring）。
3. **流失 `lost`**：上周有交易、本周没交易的站点；`tpv` = 上周金额；按 `tpv` 降序。`base` = 上周全部行金额之和；`rate = lost_tpv / base`（`base ≤ 0` → `null`）。
4. **掉量 `drops`**：两周都有交易且上周金额 > 0，`ratio = 本周 / 上周 − 1 ≤ drop_page`；`tpv` = 上周 − 本周 之和。**和流失不重叠**：本周为 0 的归流失。
5. **在途风险 `risk`**：`states` 非 `None` 时，遍历各天命中，类型 `沉默N` 且 `N ≥ 7` 的，按站点键去重（**同一站点一周里先满 7 再满 30 只算一次**，取最后那条），`tpv` = `tpv30` 之和；`states is None` → `{ok:false, tpv:null, sites:null, merchants:null, reason:"这一周的状态没跑过，算不出来"}`。
6. **前 5 家 `top`**：流失站点按 `用户ID` 合成商户，`tpv` 相加，附「谁在跟」：每个站点的 `跟进人 · 状态`（名字空则只写状态，都空写「无人认领」），去重用「、」连；`无人认领 = 跟进 == "无人认领"`；`有人跟 = 跟进里含「跟进中 / 已挽回 / 放弃」之一`。
7. `unclaimed` / `claimed` = 全部流失商户（不截前 5）里无人认领 / 真有人跟的家数。
8. 正文 `text()`：标题 `【商户流失周报】<cur 期次>`（**不带 `date`**）；在途风险 `ok:false` 时写「算不出来」不写 `$0`；「谁在跟」整段只在 `claimed > 0` 时出现。

**边界与刻意的决定**：
- 头条**走报表自带的周报行**，不从日报按 ISO 周加：报表的周是周五 → 周四，加出来的数对不上还不报错（文件头；`§2.17.7`）。
- **标题不带日期**：补跑那天 ≠ 这一周；内容永远是最新那个完整周（`§2.21.5`）。
- **在途风险窗口倒了要 `ok:false` 不能给 0**：`$0 · 0 家` 长得和「真没有风险」一模一样；`states` 传 `None` 和 `[]` 是两回事（`§2.21.5`，`risk_window()` docstring）。
- 掉量**不混进流失数**（文件头）。
- 「谁在跟」是人手填的，一条没填时整段不出现；页面照旧显示，两边规矩不一样（`§2.21.6`，`text()` 注释）。
- 「真有人在跟」看**状态**不看名字：建行时「跟进人」默认填了 BD / 代理商，非空是常态；「未跟进」和「无人认领」都不算（`§2.21.65`，`taken()`）。

**输出形状**：`{ok:true, date, prev:<期次>, cur:<期次>, window:{start, end}, lost:{tpv, sites, merchants, base, rate}, risk:{ok, tpv, sites, merchants, tier(, reason)}, drop:{tpv, sites, merchants, ratio}, top:[{用户ID, 商户名称, 直签人, 代理商名称, tpv, sites:[行], 跟进, 无人认领, 有人跟}], unclaimed, claimed}`；或 `{ok:false, date, reason}`。

**黄金用例**：`fixtures/golden/churn_weekly/头条是上周量_掉量不重叠_有人跟看状态不看名字/`、`在途风险同一站点一周只算一次/`、`在途风险窗口算不出来ok_false不给0/`（`states: null`）、`不足两个完整周ok_false/`、`没走完的那一周不算数/`。输入 `{ws, states, follow, date}`，`settings.json` 是扁平的 `{drop_page}`。正文：`churn_weekly_text/标题不带日期_谁在跟只在有人跟时出现/`、`在途风险算不出来写算不出来不写0/`。

**工作台实现**：`churn/weekly.py: summary()`、`churned()`、`dropped()`、`risk()`、`risk_window()`、`by_merchant()`、`taken()`、`text()`。

## 7 · 出单监控分档

**定义**：拿今天和昨天两份出单监控报表逐行对比，给每个站点定一个**去向**（十三档）和**落点**（通知+表 / 仅表 / 丢弃），并产出通知分组。这是整条链路里唯一决定「谁算新出单、谁算滞留」的地方（`order_monitor/classify.py` 文件头）。

**输入**：两份报表（第二张 sheet，两行表头，`order_monitor/excel.py: read_excel_sheet2`），每行用到的列：

| 列 | 类型 | 允许空 | 用法 |
|---|---|---|---|
| `用户ID` | 文本 19 位 | 不应空 | `clean_uid`：不经浮点，去掉尾部 `.0`，科学计数法用 Decimal 还原 |
| `站点` | 文本 | 空 → 丢弃（见边界） | `normalize_site`：小写、去 `https://` `http://` `www.`、去尾部 `/`；唯一键 = `用户ID|规整后站点` |
| `商户名称` | 文本 | 允许 | 只进通知 |
| `所属BD` | 文本 | 允许（空显示「未分配BD」） | 通知 / 私聊路由 |
| `累计TPV_USD` | 浮点 | 空 → 0.0 | 阈值 $100 |
| `第一笔成功交易时间` | 日期时间 | 允许空 | 有没有交易过；滞留天数 |
| `站点_商户提交时间` | 日期时间 | 允许空 | 老商户排除 |
| `提交通道时间` | 日期时间 | 允许空 | 通道审核中 / 待提交通道 |
| `通道结果反馈时间` | 日期时间 | 允许空 | 开通日；开通天数 |

日期解析（`to_date`）认 `%Y-%m-%d %H:%M:%S` / `%Y-%m-%d %H:%M` / `%Y-%m-%d` / `%Y/%m/%d %H:%M:%S` / `%Y/%m/%d`，认不出 → 空。报表其他列：六列耗时（见本节末）、七列日期、`建议进件通道`（`§2.18.2`）；`站点_审核结果` / `支付方式_审核结果` 全是 APPROVED，零信息量，故意不用（`§2.18.2`）。第三张 sheet「站点审核失败」按**名字**认，读不到返回原因不返回空表，「当日新增」按 (用户ID|站点) 集合差、没有前一天时是 `null` 不是 0（`§2.20`）。

**参数**（都是常量）：

| 常量 | 值 | 含义 |
|---|---|---|
| 出单线 | `100`（美元，字面量） | 累计 TPV 跨过 $100 算出单 |
| `STUCK_DAYS_THRESHOLD` | 3 | 距首笔满 N 天累计仍 < $100 |
| `STUCK_GROWTH_EPS` | 0.01 | 较昨日增长小于此值视为零增长 |
| 未出单分档 | 3 / 30 / 60 天 | `get_remark_by_days` |
| `PENDING_DAYS` | 180 | 「待激活」的上界 |

**算法要点**（逐行、按顺序，命中即停；每行**不多不少一条**去向）：
1. 昨天的表先建索引：`用户ID|站点` → `{tpv: 累计TPV_USD, first_txn: 第一笔成功交易时间}`（站点规整后为空的行不进索引）。
2. 今天每行：`站点` 规整后为空 → **站点为空 / 丢弃**。
3. `first_txn` 和 `站点_商户提交时间` 都有且 `first_txn < 提交时间` → **老商户排除 / 丢弃**（首笔早于建站，不属于这条漏斗）。
4. `tpv_today ≥ 100`：昨天 `tpv < 100`（含昨天没这行，取 0）→ **新出单 / 通知+表**（状态「已出单」，出单日期 = 报表日）；否则 → **存量已出单 / 仅表**（`keep`：整行照样进结果对齐字段，但不进通知）。
5. 否则若 `first_txn` 有值或 `tpv_today > 0`：昨天 `first_txn` 为空 → **测试交易 / 通知+表**；否则 `first_txn` 有值且 `(报表日 − first_txn).days ≥ 3` 且 `|tpv_today − tpv_yd| < 0.01` → **小额滞留 / 通知+表**；否则 → **小额爬坡 / 仅表**（状态「测试交易」，`keep`）。
6. 否则若 `通道结果反馈时间` 为空：`提交通道时间` 有值 → **通道审核中 / 仅表**，否则 **待提交通道 / 仅表**。
7. 否则 `days_open = 报表日 − 通道结果反馈日`（按日期部分相减）。反馈日 **等于** 报表日 → **新审核通过-待出单 / 通知+表**。
8. 否则按 `days_open` 分档：≤ 3 → `👀 3天内未出单`；≤ 30 → `🔴 3-30天未出单`；≤ 60 → `🟠 30-60天未出单`，三个都是去向 **未出单 / 通知+表**（备注留在条目里，进**日报**）；≤ 180 → 去向 **待激活 / 通知+表**（备注 `🟡 60-180天待激活`，**单独一条消息、按周发**）；> 180 → 去向 **开通>180天 / 仅表**（备注 `⏸ 开通>180天`，不进通知）。

十三档的顺序（`DISPOSITIONS`，页面和对账表按它排、全部常驻含 0 的档）：新出单、测试交易、小额滞留、新审核通过、未出单、待激活、存量已出单、小额爬坡、通道审核中、待提交通道、开通>180天、站点为空、老商户排除。落点：前六档「通知+表」，中间五档「仅表」，最后两档「丢弃」。日报通知的分段顺序 `DAILY_ORDER = [✅ 新出单, 🧪 测试交易, 🐢 小额滞留, 🆕 新审核通过-待出单, 👀 3天内未出单, 🔴 3-30天未出单, 🟠 30-60天未出单]`，「待激活」不在里面（`PENDING_ORDER` 单独一条）。

**边界与刻意的决定**：
- 那条 60 天的线 2026-09-16 改了：原来 `> 60 天` 的 68 家整批静默丢弃，而开通→首单的 75 分位是 62 天，那刀切在分布中间；现在 61~180 进「待激活」（通知+表，单独周消息），>180 只入表；**日报一字不变**（`§2.17.5`）。「待激活」是**单独一档去向**，不并进「未出单」。
- 十三档加起来必须等于报表行数；「站点为空」实测常年是 0，也要常驻显示（`§2.17`）。
- ⚠ **「站点为空」只认「全是空白字符」这一种写法**：真正的空格子被 pandas 读成 NaN，`str(NaN)` 是 `"nan"` 非空，那行会带着假唯一键 `用户ID|nan` 照常往下分类。口径没改，重写时要**决定**是照搬这个行为还是修掉，并在黄金用例里钉住（`§2.17`，`DISPOSITION_WHY`）。
- 通知元组里的 `bd` 是原始字符串，显示前要过 `owner_name`，否则群消息里出现 `BD:nan`（`§2.18.96`；那一步在工作台的 `notify.py` / `report.py`，不在本仓库）。
- 「新审核通过」只看「反馈日 == 报表日」，不含 ≤1 天档（`get_remark_by_days` docstring）；一行既 ≥ $100 又是今天反馈的，按顺序先归「新出单」。
- 存量 `keep` 档不碰「是否出单 / 备注 / 出单日期」三列（工作台 `CLAUDE.md`）。

**耗时六列（`§2.18`）**：报表自带 `站点_上线时长` / `支付方式_上线时长` / `站点_网站审核耗时` / `支付方式_网站审核耗时` / `通道审核耗时` / `集成耗时`，**单位小时、不含节假日**，一个空格子都没有；**别自己算**（自己相减是自然日，偏大三成）。每列的 `0` 有四种意思，只有一种是真耗时，靠起点 / 终点日期分（`static/js/order_monitor/analyze.js: START_DATE_OF / END_DATE_OF`；台账里日期列名把「时间」改成了「日期」，`order_monitor/report.py: DATE_COLS`）：

| 耗时列 | 起点 | 终点 |
|---|---|---|
| 站点_上线时长 | 站点_商户提交日期 | 第一笔成功交易日期 |
| 支付方式_上线时长 | 支付方式_商户提交日期 | 第一笔成功交易日期 |
| 站点_网站审核耗时 | 站点_商户提交日期 | 站点_风控审核日期 |
| 支付方式_网站审核耗时 | 支付方式_商户提交日期 | 支付方式_风控审核日期 |
| 通道审核耗时 | 提交通道日期 | 通道结果反馈日期 |
| 集成耗时 | 通道结果反馈日期 | 第一笔成功交易日期 |

判定顺序（`timingSplit`）：格子不是数 → `missing`；终点日期没有 → ① 还没走到这一步（不进分母）；起点日期没有 → ② 算不出来（不进分母）；终点早于起点 → ③ 上游算出负数写 0，算不出来（不进分母）；其余进分母，其中值为 0 的是 ④ **真的秒过**。「还在路上」的右栏判定是**没有第一笔成功交易日期**，不是「上线时长 == 0」（老商户那批也是 0 但早有交易）；右栏用自然日含周末，左右不是同一把尺子。按 `建议进件通道` 分组看耗时时只有「通道审核耗时」是干净的因果，出单率那列别单看（`§2.18.2`）。

**输出形状**：`classify_from_excel` 返回 `(results, notify)`；传 `audit=[]` 时每行追加一条。
- `results[]`：`{site_key, row:<原行>, action: new_order|keep|test_txn|stuck|set_status|new_approved|update_remark, status, remark(, order_date)}`。
- `notify`：`{档名: [(用户ID, 商户名称, 站点原文, 所属BD原文, 通道反馈时间, 首笔时间, 累计TPV, 档名)]}`。
- `audit[]`：`{行号(位置下标), 用户ID, 商户名称, 站点, 所属BD(空格子给空串), 去向, 落点, 累计TPV_USD, 开通天数, 备注}`；`累计TPV_USD` / `开通天数` 没算到的档是 `null`。

**黄金用例**：`fixtures/golden/order_monitor_classify/五档各一行_含站点空丢弃与超180天只入表/`：新出单 / 测试交易 / 3天内未出单（通道反馈日比报表日早一天，**不是**「新审核通过」，后者只认反馈日等于报表日）/ 开通>180天只入表 / 站点空丢弃，各一行；输出 `{results: [results, notify], audit}`。expected 由 pandas 或它的最小替身生成（`scripts/生成黄金用例.py: _pandas_shim`），两者对这族输入逐字节一致，前提（输入无 null、每行键一样）由 `tests/golden.py` 钉着。`results[].row` 落盘成 dict。

**工作台实现**：`order_monitor/classify.py: classify_from_excel()`、`get_remark_by_days()`、`DISPOSITIONS` / `DISPOSITION_SINK` / `DISPOSITION_WHY`；读表与类型 `order_monitor/excel.py: read_excel_sheet2()`、`read_reject_sheet()`、`clean_uid()`、`normalize_site()`、`to_float()`、`to_date()`；台账与耗时列 `order_monitor/report.py: save_ledger()`、`DURATION_COLS`、`DATE_COLS`、`ATTR_COLS`；耗时四种 `0` 的判定 `static/js/order_monitor/analyze.js: timingSplit()`。

## 8 · 生命周期漏斗

**定义**：五级 `注册 → 开通 → 首单 → 稳定出单 → 沉默`，每级几个站点 / 几家商户；两段耗时（注册→开通、开通→首单）的中位数和分位；卡在哪一级的已经等了多久（`churn/funnel.py` 文件头）。

**输入**：
- `detail`：出单监控台账的「明细」行，用到 `用户ID`、`站点`、`站点_商户提交日期`、`通道结果反馈日期`、`第一笔成功交易日期`（`YYYY-MM-DD`，只取前 10 个字符；空 / 垃圾算没有）。`用户ID` 或 `站点` 空的整行不算。
- `state`：第 4 节的输出（用 `sites[key].silent_days`），可 `null`。
- `settings`：用 `silence_days`，不传时用 `state.settings`，都没有 → `[2]`。
- `date`：**这份台账自己那天**（不传用运行日 —— 重写时必须传，否则不确定）。

**参数**：`LEVELS = ["注册","开通","首单","稳定出单","沉默"]`（顺序走数组）；`STEPS` = 两段；`RULER = "自然日 · 含周末"`；沉默门槛 `tier = silence_days[0]`。

**算法要点**：
1. `注册` = 有提交日期的行；`开通` = 注册里有通道反馈日期的；`首单` = **开通里**有首笔日期的（有首笔但没反馈日期的行不进「首单」）。
2. 后两级：`首单` 里的站点，在 `state.sites` 里 `silent_days ≥ tier` → `沉默`，否则 → `稳定出单`；**状态里没有这个站点 → `uncovered`，单独数，不当成稳定出单**。
3. 每级给 `{sites: 行数, merchants: 用户ID 去重}`。
4. 两段耗时（`step_stats`，对**全部**有效行算）：起点、终点都解析；起点缺 → `no_start`（两头都没有也算这里）；终点缺 → `no_end`（还没走到，是「卡住的」）；终点早于起点 → `negative`；其余 `(终点 − 起点).days` 进样本。给 `median`、`n`、`p75`、`p90`（`round(q × (n−1))` 取位）、三个排除数、`ruler`。样本空时 `median` / 分位 → `null`，**不是 0**。
5. 卡住 `stuck`：「提交了没通过」= 注册里不在开通的，等待天数 = `date − 提交日`；「通过了没首单」= 开通里不在首单的，等待 = `date − 反馈日`；终点早于起点的不算；给 `{name, note, sites, merchants, median, n, ruler}`。

**边界与刻意的决定**：
- 耗时一律**自然日含周末**，一张表一把尺子；报表自带的六列是小时不含节假日，两把尺子混在一起读的人分不出，所以界面上写明并指回出单监控页看那六列（文件头；`§2.18`）。
- 起点缺 / 终点缺 / 终点早于起点三种分开数、都不进分母，不当 0（文件头；同 `§2.18` 那四种 `0`）。
- `date` 是台账那天，不是今天：看三天前那份台账时拿今天当终点会把每行多算三天（`build` docstring）。
- 状态没覆盖到 ≠ 稳定出单：混进去那一级会虚高，而那正是老板最想信的那个数（`build` 注释）。

**输出形状**：`{ok:true, date, ruler, levels:[{name, sites, merchants}×5], steps:[{from, to, median, n, ruler, no_start, no_end, negative, p75, p90}×2], stuck:[{name, note, sites, merchants, median, n, ruler}×2], uncovered:{sites, merchants}, tier}`。

**要点**（每条都有 `§` 或 README 出处）：
- 读任何比率字段走 `toRate()`（`'99.99%'` → 0.9999），不走 `num()`（只抹 `%` 不除 100）；用错两级放大，两级都不报错（`§3`）。
- 漏斗恒等式：`支付单支付成功率 = 环节2 × 环节3 × 环节4`，`业务单支付成功率 = 环节1 × 支付单支付成功率`；172 组零反例，**和重试无关**（`§2.13`）。
- 支付前 / 支付中两段拆账只看分子分母、不拿比率相乘：`PO单数 − 成功单 = (PO单数 − 支付单数) + (支付单数 − 成功单)`；缺行进 `noData` 不当 0；本期没走完不给单量环比（`§2.16`）。
- 失败原因归类**看编码不看文案**：`ZFFK*` → 风控拦截（我方）、`ZF3D*` → 3DS验证失败，`ZFWG*` 或无编码 → 网关拦截再按关键词拆；`SUB_RULES` 顺序就是口径；没命中的兜底进「发卡行拒绝」但兜底笔数单独数（`§2.15`）。
- 两个白名单（`ALLOWED_SOURCES` / `METRIC_CANON`）认不出就静默丢，`formatDrift()` 列出认不出的（`§2`）。
- 来源覆盖缺口是常态（0.2%~1.6%），阈值 5%；算不出来必须 `ok:false` 不当 0（`§2.12`）。
- 环节2 没有子指标，它告警不算「未解释」，这一档界面和播报里一个字都不出（`§1.5`）。
- 排序 / 取舍 / 严重度看**折损单量**不看影响比率（pt 跨环节不可比）；涨的时候不能叫「问题」（`§2.5`）。
- 「待观察商户」不是告警；「连续 N 期」跟周期走；门槛 10 单不是 50；基准用不加权中位数（`§2.6`）。
- 跨来源的同一商户**按来源分开算，不合并**——故意的（`§2.75`）。
- 「重点关注商户」是扫全部商户排出来的，头条数字用源表真值（`§2.8`）。
- 趋势期次走自然序、缺环节断线（`§2.9`）。
- 基准线按「来源×指标」分池三级回退；水平信号不做混池；满分指标挡掉；「常年趴在 60%」报不出来是故意的（`§2.10`）；本机存档算基准线要按 (期次, 来源, 指标) 去重、均匀取样（`§2.11`）。
- 环比按选的那对日期现算，源表那列只做校验，`parseDodCell()` 按形态判不按大小（README「环比：现算」）。
- 喂 AI 的表截断必须自报、合计行不许丢、残差只加计数列（`§2.16.5`）；日报 / 周月报两套提示词口径别合回一套（`§2.14`）。
- 播报是两条消息，里面不写口径、不出现「工作台」三个字（`§2.5` `§2.6`）。
