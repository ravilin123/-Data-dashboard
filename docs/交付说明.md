## 2 · 怎么验收

**一条用例 = 喂 `input.json` + `settings.json`，输出和 `expected.json` 逐字节相等。**

每族怎么调（照 `scripts/生成黄金用例.py: run()`，重写时按同样的入参映射）：

| 族 | 调什么 | 入参从哪来 |
|---|---|---|
| `names` | `owner_name(x)` 逐个 / `is_agent_id(x)` 逐个 | `input.raw[]` 或 `input.names[]`；输出是数组 |
| `churn_assess` | `assess(days, today, prev, settings, gateway)` | `input.days` `input.today` `input.prev`（可 null）`input.gateway`（可缺）；`settings.json` 整份当 `cfg` |
| `churn_overview` | `overview.build(days, date, n_days, top_n)` | `input.days` `input.date` `input.n_days`（默认 30）`input.top_n`（默认 10） |
| `churn_trade` | `trade.build(days, date, period, n, metric, top_n, anchor=…, weeks=[])` | `input.days` `date` `period`（默认 日）`n`（默认 12）`metric`（默认 tpv）`top_n`（默认 10）`anchor`；`weeks` 用 `input.weeks`，没有就传空列表 |
| `churn_daily` | `daily.summary(state, settings)` | `input.state`（是 `assess` 的输出）；`settings.json` 整份 —— ⚠ 见第 4 节那条 |
| `order_monitor_classify` | `classify_from_excel(今天表, 昨天表, date, audit=[])` | `input.today[]` / `input.yesterday[]` 各是一张表的行；输出 `{"results": …, "audit": …}` |
| `churn_assess_chain` | 按 `input.dates` 顺序逐天调 `assess(days, d, prev, settings, gateway)`，`prev` = 上一天的输出（`ok:false` 的那天不更新 prev） | 输出 `{dates, hits:{日期:[类型]}, states:{日期:状态}}` |
| `churn_weekly` | `weekly.summary(ws, states, settings, follow, date)` | `input.ws`（周台账列表）`input.states`（可 null）`input.follow` `input.date`；`settings.json` 扁平 `{drop_page}` |
| `churn_funnel` | `funnel.build(detail, state, settings, date)` | `input.detail` `input.state` `input.date`；`settings.json` 空 = 用 `state.settings` |
| `churn_trade_drill` | `trade.drill(days, date, period, filters, metric, limit, anchor)` + `trade.options(days, date, period, anchor)` | 输出 `{drill, options}` |
| `conversion_funnel` | JS `funnel.js`：`toRate` 逐个、`chainDenom(row, metric, suffix)`、`calcFunnel(...)`、`hasDenomChain` 逐个 | `scripts/golden_js.mjs` 里那几行就是调法 |
| `conversion_coverage` | JS `coverage.js`：`coverageCheck(scenePOBySource(rows), date)` | `input.rows` 是场景行（带 `_n` / `_d`） |
| `conversion_analyze` | JS `analyze.js`：`analyze(dataset, opts)` —— 转化率**整条链** | `input.dataset` 是字面量 `Dataset`；输出就是 `AnalysisResult`，键很多，都要比 |
| `shared_fail_group` | JS `shared/fail_group.js`：`groupFailures(rows, {methodOf})` | `input.rows` 带 `fail_code` / `fail_reason` / `pay_method` |
| `merchant_status` | JS `merchant/util.js`：`stClass` 逐个、`excludePending(rows)` 取 status | |
| `merchant_change_attrib` | JS `merchant/charts_data.js`：`changeAttrib(groupMetric(本期), groupMetric(上期), 'm')` | `input.last` / `input.curr` 是 `[[取值, 总数, 成功数], …]`，先按它造行再 `groupMetric(rows, 'm', null, false)` |
| `churn_daily_text` | `daily.text(daily.summary(state, settings))` | 输出 `{text}`；空串 = 一条都不该报 |
| `churn_broadcast` | `broadcast.pushable(state)` → `group_text(state)`、`group_for_dm(hits)` 每个直签人 `bd_text(owner, hits, state)` | 输出 `{pushable:[key], group_text, dm:{直签人: 文本}}`；`settings.json` 空 = 用 `state.settings` |

| `conversion_level` | JS `level.js`：`levelSignals(rows, {tDate, bl})` | `bl = {baseline:{v:2, bySrc:{}, mixed:{}, level: input.level, levelMixed: input.levelMixed}, active:true}` |
| `conversion_trend` | JS `trend.js`：`buildTrend(rows, {limit})` | 输出 `{dates, measures, partial, po, series:{measure:{来源:[值或 null]}}, sources}` |

| `conversion_po_rate` | JS `po_rate.js`：`buildPoRate(rows, {tDate, yDate})` | 场景行带 `_n` / `_d`；`当期值` 故意写 99.99% 验证只认分子分母 |

**JSON 落盘规则**（`scripts/生成黄金用例.py: dump()`，逐字节比的前提）：
- 键**按字符串排序**（Python `sort_keys=True`：按 Unicode 码点比较），所有层级都排。
- `ensure_ascii=False`：中文直接 UTF-8 输出，不转义。
- `indent=1`：每层缩进 **1 个空格**；元素之间 `,` 后换行；键值之间 `: `（冒号 + 一个空格）。
- 文件末尾一个换行符 `\n`。
- 浮点保留原值：Python 的 `repr`（最短往返表示），`1000.0` 就写 `1000.0`（不写 `1000`），`0.631579` 就写 `0.631579`；口径层已经用 `round(x, 2)` / `round(x, 6)` 定了小数位，重写时先按同样的位数四舍五入再序列化。**整数和浮点是两种值**：`"orders": 16` 和 `"tpv": 16.0` 不能互换。
- `null` 就是 `null`，不是 0、不是空串、不是缺键；`true` / `false` 小写。
- tuple 落成数组；`datetime` 落成 `str()`（`2026-09-17 00:00:00`）。
- 空 dict `{}` 和空数组 `[]` 各自写成一行。

如果目标语言的 JSON 库做不到逐字节一致（比如浮点 `repr` 不同），退一步也要做到：**解析后结构相等、数值精确相等（不带容差）、`null` 位置一致、数组顺序一致**。但先试逐字节，差在哪一目了然。

本仓库自己跑：`python tests/golden.py`（零依赖，重跑口径层和 expected 比；`order_monitor_classify` 那族没装 pandas 会说「跳过」，不算过）。

## 3 · 两个必须参数化的口径

1. **周锚点**（周从星期几开始）。工作台的周是**周五 → 周四**，报表定的，周号按**结束日**算（`docs/坑.md §2.17.7`）；公司看板现在是**周日起**。`churn/trade.py: build(..., anchor=…)` 把它做成了显式参数（0=周一 … 4=周五 … 6=周日），黄金用例 `churn_trade/周五到周四_锚点4_周号按结束日` 和 `周日起_锚点6_同一批数分桶不同` 各钉一个。重写时**不许写死**；过渡期两种口径并存，改公司口径的事另谈（`docs/specs/看板/计划.md` Q25）。
2. **日界**。工作台的「一天」是报表里 `统计周期` 那一列给的日期，台账按它落盘，口径层本身不做时区换算；公司看板是「UTC+8 自然日」。两边的「今天」是不是同一段时间，要拿到公司数据字典之后核（`docs/数据字典对照.md` 末尾）。重写时把「一行属于哪一天」做成适配层的一个明确步骤，别散在口径里。

顺带两个已经是参数的：`silence_days` / `drop_push` / `drop_page` 等全部在 `churn/config.py: DEFAULTS`；数字读法 `null` / 空串回默认、`0` 要留住（`§2.18.98`）。

## 4 · 要留神的几件事

- **`order_monitor_classify` 的 expected 是 pandas 的最小替身生成的**（`scripts/生成黄金用例.py: _pandas_shim`，落地那台机器装不了 pandas）。对这族输入（全是 str / float、每行键一样、没有 null），真 pandas 的 `DataFrame(...).iterrows()` 不会改任何值，两者逐字节一致；`tests/golden.py` 钉着这个前提。你在装了 pandas 的机器上跑 `python tests/golden.py`，`--check` 那一步就是用真 pandas 比的。`results[].row` 落盘成 dict（NaN → null）。
- **`churn_daily` / `churn_daily_text` / `churn_weekly` / `churn_weekly_text` 的 `settings.json` 是扁平的**（`daily.summary()` / `weekly.summary()` 读扁平 dict，不认 `{"churn": {...}}`）；`churn_assess` / `churn_assess_chain` / `churn_broadcast` 那几族是整份 `cfg`（带 `churn` 段或为空）。两种形状**不一样**，照表里写的传。
- 状态机有两种用例：`churn_assess`（单日、`prev: null`）和 `churn_assess_chain`（多日连跑，每天喂前一天的输出）。重写「昨日状态」那条线要拿后者验。
- 文本四族（日报 / 播报 / 周报 / 交易量群消息）不要求你逐字复现措辞，但**「什么时候是空串」**是契约（空串 = 调用方记「没跑」不发），要一致。

## 5 · 内网到不了 GitHub 时打包什么

最少这三个目录，直接拷走：

```
docs/                 口径.md、交付说明.md、数据字典对照.md、坑.md、specs/
fixtures/golden/      黄金用例（输入 + settings + expected）
contracts/            日报契约 schema + 校验器
```

建议再带上参考实现和它的用例，读文档有疑问时直接看代码：

```
names.py  churn/  order_monitor/            Python 口径层
static/js/conversion/  static/js/merchant/  static/js/shared/  static/js/order_monitor/analyze.js
tests/                                       同步来的纯函数用例（当说明书读）
scripts/生成黄金用例.py  tests/golden.py     怎么喂、怎么比
口径清单.json  同步记录.json                 哪些文件算口径层、同步自哪个 commit
```

不要带：`config.json`（凭据）、`data/`（真实台账）、任何 `$WB_FIXTURES` 里的真实报表。仓库里本来就没有真实商户数据，打包前 `grep -rn '"用户ID": "' fixtures/ | grep -v 10000000000000000` 应该一行都没有。

## 6 · 有问题找谁、怎么改

- 口径**以工作台为准**：这里的代码是镜像，发现口径要改回工作台改、跑那边的测试、再同步（本仓库 `CLAUDE.md` 三条不许破的第一条）。
- 读文档和读代码对不上时，以代码和 `tests/` 为准，并在回复里指出是哪一句。
- 公司这边要问的五件事（`docs/specs/看板/计划.md`）：技术栈、有没有站点级 / 商户级明细接口、「映射管理」和工作台 `agent_owner` / `bd_emails` 谁为准、数据字典、改周口径找谁谈。
