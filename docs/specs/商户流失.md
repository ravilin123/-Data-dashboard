# 商户流失监控 · spec

2026-09-15 由 `/grill-me` 六轮问答固化。数据依据：FlyPay 独立站收单统计表（2026-09-14 那份 +
tpv-sync 攒下的 24 份日报，拼出 2026-07-31 ~ 09-14 连续 46 天）、站外_网关TPV统计报表（2026-08-06）、
FlyLink 业务统计表（只做参考）。三份原始数据都是真实商户数据，**不进仓库**。

术语沿用仓库口径：**播报**（发到飞书群的消息）、**台账**（本机每天落一份的运行记录）、
**底账**（飞书多维表格里那份全量对齐的表）、**落点**（一行数据最后去了哪：通知+表 / 仅表 / 丢弃）、
**静默**（silent 模式：只记表不发人）、**补跑**（关机漏掉的日子开机后串行跑）、**存档**（邮箱附件按业务日期落盘）。
本 spec 新增的词：**站点**（用户ID + 站点，流失的判定单位）、**沉默天数**（报表日 − 最后一个有交易日）、
**跃迁**（沉默天数第一次跨过 2 / 7 / 30）、**前 30**（最近 30 天滚动 TPV 排前 30 的站点，推送资格）、
**在途风险**（本周新进沉默 ≥7 天的站点各自最近 30 天 TPV 之和）、**通道异常**（同一网关当天多家一起掉）。

---

## Problem Statement

老板说「流失 95%」，运营负责人感觉流失严重、总盘子在掉，但手上没有任何东西能回答「谁在流失、
从哪天开始、归谁跟」。核过数据之后问题其实是这样的：

- 95% 那个数是**买家**当天不复购，不是商户。FlyPay 独立站的商户月流失率在家数上是 26%~27%，
  流失家占上月 TPV **18%~20%**，每月靠新商户补回来 —— 是漏桶，不是缩桶。
- 工作台现有四个页面**没有一个能看见「出过单的商户停了」**：出单监控只盯从 0 到 $100 的新商户，
  越过 $100 进 `keep` 档之后永久隐身；转化率页的「掉量」是「本期一行都没有」，不是下滑；
  系统里没有任何「最近一次出单时间」。
- 开通超过 60 天没出单的 68 家被出单监控静默丢弃（`docs/坑.md` §2.17），而开通→首单的 75 分位是 62 天，
  那一刀正好切掉四分之一最终会出单的商户。
- 之前做的 tpv-sync 已经在把 FlyPay 日报同步到飞书，但跑得不稳（30 次启动 18 次跑完），
  且多站点商户被并成一行，日维度少 5.2% 的 TPV。
- 现在发现流失靠人翻表，跟进靠人记，几乎处于「没人跟」的状态；而一旦流失基本救不回来，
  所以发现必须早、名单必须短、必须落到具体的人。
- 所有分析都要人打开页面点按钮。用户明确要求：**定时任务 + 推送 + 自动记表，不由人来点**，
  包括已有的转化率播报。

## Solution

工作台新增第五个页面「商户流失」，配一个通用的定时 job 注册表，每天 10:30 一轮跑三个 job：
出单监控 → 转化率 → 商户流失。商户流失 job 从每天邮件到的 FlyPay 日报和网关报表叠出**永不清理的
本机台账**，对每个站点跑「沉默 2 / 7 / 30 天」状态机和「日环比 ≤−70%」预警，只把**前 30 个站点**的命中
推到群和对应 BD 的私聊，其余全部记进页面和多维表格；每周一给老板一份三行摘要，「谁在跟」从
多维表格里 BD 手填的三列回读。转化率播报改成定时发，周报月报在「已走完的周期第一次出现在报表里」
那天发，AI 总结只私聊给运营负责人审。出单监控的 60 天那刀放到 180 天，单独一档「待激活」。
FlyLink 只留适配层的口子。

## User Stories

**看清流失**

1. 作为运营负责人，我想在一个页面上看到「注册 → 开通 → 首单 → 稳定出单 → 沉默」每一级有多少家、卡在哪，
   这样我能说清流失发生在生命周期的哪一段，而不是笼统一句「流失严重」。
2. 作为运营负责人，我想看到每个站点「距最后一个有交易日多少天」，这样「停了」这件事第一次有了数字。
3. 作为运营负责人，我想沉默名单按商户分组、站点为行，这样一家七个站点的商户不会占七条把别人挤掉。
4. 作为运营负责人，我想名单按最近 30 天滚动 TPV 排序，这样最先看到的是最值钱的那几家。
5. 作为运营负责人，我想零星型商户（30 天里只出过几天单）在名单上被标出来，这样它的「沉默」不会被当成事故。
6. 作为运营负责人，我想看到入网那一级（注册超 7 天未开通、开通超 N 天未首单）的家数和中位耗时，
   只盘点不催，因为审核在风控那边催不动，但数字要有。
7. 作为运营负责人，我想看到「主动清退 / 自然流失」暂时**没法拆**这件事明写在页面上，
   而不是一个看起来拆过的数字，因为风控关停没有名单来源，只能标「停交易」。

**沉默告警**

8. 作为运营负责人，我想一个站点沉默满 2 天时收到一次提醒，满 7 天、满 30 天再各一次，
   之后不再重复，这样名单上不会天天是同一批名字。
9. 作为运营负责人，我想站点恢复交易后状态归零、页面标「已恢复」但不推送，这样恢复不制造噪声。
10. 作为运营负责人，我想状态机对**全部**站点跑、全部记进页面和多维表格，但每天只推前 30 个站点里的命中，
    这样群里每天大约一两条，还有人看第二眼。
11. 作为运营负责人，我想「前 30」用最近 30 天滚动 TPV 算，和沉默用同一把尺子，这样月初不会因为上月归零而排空。
12. 作为运营负责人，我想台账缺了几天时状态机不在那段区间乱跃迁、页面显示缺口，补齐后回填，
    因为「算不出来」必须是算不出来，不能当成沉默也不能当成活跃。

**掉量预警**

13. 作为运营负责人，我想前 30 站点日环比 ≤−70% 时收到预警，≤−50% 只在页面上看，
    这样每天大约 0.6 条、三分之一噪声，而不是 1.8 条、一半噪声。
14. 作为运营负责人，我想掉量在两天内回到原水平 80% 以上时自动关闭、不再提，因为那是波动不是流失。
15. 作为运营负责人，我想周环比 ≤−50% 的站点不单独推，只进周一摘要并单独列，因为周的口径太慢，
    但老板要看。

**推给对的人**

16. 作为 BD，我想每天只收到我名下、且在前 30 命中里的站点，这样我不会因为几十家零星商户天天沉默而把机器人静音。
17. 作为运营负责人，我想直签人是代理商 ID 或空白的站点推给一个配置里的兜底人，名单上标「代理商：某某」，
    这样接的人知道该找谁，而不是没人收。
18. 作为运营负责人，我想以后维护一张「代理商 → 负责 BD」的对应表时不用改代码，只改配置。
19. 作为运营负责人，我想 BD 姓名到邮箱的对应沿用出单监控那份名单和它的规矩（对不上就不发、整个替换才删得掉人），
    这样两套监控不会出现两份名单各说各话。
20. 作为运营群成员，我想群消息里出现的是站点、商户名、沉默天数、30 天 TPV 和标签，没有口径解释句，
    也不出现字面量 `nan`。
21. 作为运营负责人，我想每天没有任何命中时群里**不发**流失消息（名单类消息空了就不发，同待观察商户的规矩），
    但台账里记着这天跑过，这样「没事」和「没跑」分得开。

**老板的周摘要**

22. 作为老板，我想每周一收到一条私聊，头条只有一个数：上周活跃、本周一笔没有的站点的上周 TPV 之和，
    这个口径和报表自带的「流失率」一致，我拿别的表能对上。
23. 作为老板，我想第二行看到「在途风险」：本周新进沉默 ≥7 天的站点最近 30 天 TPV 之和，这样知道下周还会掉多少。
24. 作为老板，我想掉量（周环比 ≤−50%）单独一行，不混进流失的数。
25. 作为老板，我想看到前 5 家和每家「谁在跟」，没人填就明写「无人认领」，这样我知道该问谁。
26. 作为运营负责人，我想这条摘要同时抄送运营群，这样老板问起来时群里的人已经看到了同一份。

**跟进闭环**

27. 作为 BD，我想在飞书多维表格里直接填「跟进人 / 跟进状态 / 备注」，不用登录工作台，
    因为我本来就在飞书里。
28. 作为运营负责人，我想工作台把这三列读回来，显示在页面和周摘要里，这样跟进状态只有一份真相。
29. 作为运营负责人，我想「跟进状态」是固定的四档（未跟进 / 跟进中 / 已挽回 / 放弃），这样能统计不能自由发挥。

**数据接入**

30. 作为运营负责人，我想 FlyPay 独立站收单统计表和站外网关报表像转化率报表一样从邮箱自动存档，
    只要在邮箱规则里加两条主题关键词，不要新的抓邮件工具。
31. 作为运营负责人，我想每天的日报叠成一份永不清理的本机台账（站点级：金额、笔数），
    因为报表本身没有任何日期列，「沉默几天」只能靠叠出来。
32. 作为运营负责人，我想 tpv-sync 攒下的 24 份日报一次性灌进台账，这样上线第一天就有 46 天历史，
    「沉默 30 天」立刻能算。
33. 作为运营负责人，我想同一天在不同文件里出现时后来的覆盖先来的（实测只有 0.07% 不一致），不要报错停下来。
34. 作为运营负责人，我想多站点商户按站点分开记，永远不合并，这样不再少 5.2%。
35. 作为运营负责人，我想沉默站点带一个标签说明这家商户在网关报表里当天还有没有交易（「其他通道仍有交易」
    或「全网关停止」），这是唯一能拿到的「为什么」。
36. 作为运营负责人，我想同一个网关当天多家一起掉时群消息里单独一行「通道异常」，每条受影响的告警都带这个标签，
    这样 BD 不会挨个去问商户。

**飞书多维表格**

37. 作为运营负责人，我想 tpv-sync 写的 TPV 日 / 周 / 月三张表继续由工作台每天写，
    看板和切片器不用重连。
38. 作为运营负责人，我想这三张表加「站点」列、键改成三段，14 家多站点商户的旧行清掉重写，
    清理之前先 dry-run 给我看会删哪些行。
39. 作为运营负责人，我想新建一张「商户流失」表记每次命中和标签，列名我在飞书里手建，README 给我清单，
    改了列名有用例会挂。
40. 作为运营负责人，我想表里的数字列发数字不发字符串、用户 ID 是文本列，和其他三张表的规矩一样。

**出单监控的改动**

41. 作为运营负责人，我想开通 61~180 天未出单的商户不再被丢弃，而是单独一档「待激活」，
    有自己的消息和落点，不混进现有的出单通知。
42. 作为运营负责人，我想超过 180 天的只入表不推送，这样它们至少在底账里能查到。
43. 作为 BD，我想「待激活」的名单按周收，而不是每天，因为这批商户变化慢，天天推是骚扰。

45. 作为运营负责人，我想以后加一种分析只要在 job 注册表里加一条（名字 / 周期 / 跑什么 / 推哪 / 记哪张表），

46. 作为运营负责人，我想机器关机几天后开机自动补跑漏掉的日子，串行、除最后一天外静默，和出单监控现在的规矩一样。

## Implementation Decisions

### 范围

- 只做 FlyPay 独立站。FlyLink 报表结构不同（多日期列和状态列），只在适配层留可选字段，不接。
- 不做买家留存、不和老板对账、不拆主动清退（没有风控关停名单）、不做入网催审动作（催不动）。

### 数据来源与适配层

- 新增两种邮箱报表：FlyPay 独立站收单统计表、站外_网关TPV统计报表，都每天邮件到。
  接入方式是邮箱规则加两条（主题关键词 + kind），走现有的匹配 / 存档 / 索引 / 状态那一条路径；
  主题里的关键词和日期位置上线时人核一次。
- 适配层输出**公共字段**：报表类型、统计周期、用户ID、站点、商户名称、直签人、代理商ID、代理商名称、
  接入模式、交易金额（美元）、交易笔数。FlyLink 的开通时间 / 首笔 / 最近一笔 / 业务状态作为**可选字段**预留。
- 用户ID 是 19 位文本，读取时禁止经过浮点（2^53 会丢精度）；网关报表的用户ID 是文本，与独立站报表精确匹配。
- 多站点：同一天同一用户ID的多行按站点分开，永不合并（实测 14 家、最多 7 行）。

### 台账

- 每天一份站点级台账（用户ID、站点、商户名称、直签人、代理商、接入模式、金额、笔数），**永不清理**；
  xls 存档照旧按天数清。
- 每份报表带 7 天日报窗口，落台账时后来的文件覆盖同一天（不一致率 0.07%，不报错）。
- 上线时用 tpv-sync 的 24 份附件一次性灌 46 天。灌数在用户本机做，附件不进仓库。
- 台账缺口（连续缺 7 天以上才会真缺）：状态机对缺口区间**不产生跃迁**，页面显示缺口，补齐后回填。

### 流失状态机（站点级）

- 沉默天数 = 报表日 − 最后一个有交易日（交易笔数 > 0 的日子）。
- 沉默状态：活跃 → 沉默2 → 沉默7 → 沉默30，每档跨过时产生一次跃迁；恢复交易回到活跃并记「已恢复」（只在页面）。
- 掉量状态：日环比 ≤ −70% 为「掉量·推」、≤ −50% 为「掉量·页面」；两天内任一天回到前一日水平的 80% 以上即自动关闭。
  日环比在台账上现算，报表自带的环比列只做校验（同转化率页的规矩）。
- 周掉量：周环比 ≤ −50%，只进周一摘要，单列。
- 推送资格：跃迁发生当天该站点在最近 30 天滚动 TPV 前 30。资格在命中时算，不回溯。
- 零星型：最近 30 天活跃天数 ≤ 10 的站点打标签，名单上带「30 天里只出过 N 天单」。
- 网关标签：沉默站点当天在网关报表里该用户ID有任何网关有交易 → 「其他通道仍有交易」，否则「全网关停止」。
- 通道异常：同一网关当天有 ≥ N 家（默认 3，可配）前 50 商户掉量或沉默 → 群消息单独一行，受影响的告警各带标签。
- 状态和跃迁全部持久化（一天一份），重跑同一天结果幂等。

### 推送

- 每天一条群消息：前 30 命中（沉默跃迁 + 掉量·推）+ 通道异常行；无命中不发，台账记「已跑·无命中」。
- BD 私聊：同一份命中里属于他的。直签人是姓名 → 现有 BD 邮箱名单（对不上不发、整个替换）；
  直签人是 19 位 ID（代理商）或空 → 兜底人，条目标「代理商：<代理商名称>」。
  预留「代理商ID → BD 姓名」的可选配置，填了就按它路由。
- 周一摘要：私聊老板（邮箱，与 BD 私聊同一种收件方式）+ 抄送运营群。
  头条 = 上一个完整周活跃、这一周一笔没有的站点，其上一周 TPV 之和，**直接用报表自带的周报行**算，
  和报表「流失率」同口径；第二行 = 在途风险；第三行 = 周掉量单列；然后前 5 家 + 谁在跟（回读列，空 → 「无人认领」）。
- 群消息里不写口径解释、不出现「工作台」三个字、不出现 `nan`（沿用 §2.5 / §2.6 / §2.18.96）。
- 四档 mode（both / group / dm / silent）与出单监控两处一字不差。

### 多维表格

- TPV 日 / 周 / 月三张表续用（看板挂在上面）：加「站点」列，键改为 统计周期 + 用户ID + 站点；
  一次性清理脚本删掉多站点商户的旧行再重写，先 dry-run 列出将删的行，同一套 sender 注入（不注入 = dry-run）。
- 新表「商户流失」：日期、用户ID、站点、商户名称、直签人、代理商、类型（沉默2 / 沉默7 / 沉默30 / 掉量 / 恢复 / 通道异常）、
  沉默天数、日环比、30天TPV、30天活跃天数、标签、是否前30、已推送、跟进人、跟进状态、备注。
  列人手建，README 列清单，用例钉列名；数字列发数字，用户ID 文本列。
- 回读：跟进人 / 跟进状态 / 备注 按（用户ID, 站点）取最新一行；读不到 = 无人认领。
  跟进状态四档：未跟进 / 跟进中 / 已挽回 / 放弃。
- 三张表配置沿用 `feishu.bitable.tables.<名>` 的方式，没配的表跳过并说清去哪填。

### 出单监控

- 「开通>60天」那刀改为 180 天：61~180 天进「待激活」档，落点为通知+表，**消息单独一条**（按周发，与 3-30 / 30-60 天同一周期），
  底账表里的去向写「待激活」；>180 天落点为仅表。对账不变：每行不多不少一条去向。
- 这条改的是 2026-09-09 的决定，`docs/坑.md` 加一条新编号记录，§2.17 原文加一行指过去。

### 定时任务

- job 注册表：名字、周期（daily / weekly:<weekday> / monthly:<day> / 周期走完才发）、依赖的报表种类、跑法、
  推哪、记哪张表。固定顺序：出单监控 → 转化率 → 商户流失。
- 每天 10:30 一轮：先收邮件再跑 job。示例配置默认从 10:00 改为 10:30；用户本机配置自己改。
- 开机补跑、漏天串行、除最后一天外静默、上限只补最近 N 天、失败即停 —— 沿用现有自动补跑逻辑，
  扩展到多 job；一个 job 失败不阻塞后面的 job，只在台账和首页标出。
- 每个 job 每天一条运行记录：没跑 / 失败 / 成功，附发送情况数组。
- 同一天重跑不重发：按（job, 周期键）落盘「已发」标记，沿用邮箱模块现有的「已分析」标记机制。
- Windows：提供登录时隐藏启动工作台的计划任务安装脚本；job 不各自注册计划任务。
- tpv-sync 退役：并行跑几天核对三张表一致后停掉它的计划任务；它的配置文件含 AppSecret，不导入仓库。
- 密钥经环境变量下发，不上命令行（沿用出单监控的规矩）。

### 转化率 job

- Python job 起 Node 子进程跑现有纯函数链（读表 → Dataset → analyze → 两条播报文本 → 三张表的行），
  Node 里读磁盘存档算基准线；子进程吐 JSON，Python 走现有飞书中转发送和写表。不驱动页面，不用 Playwright。
- 周期走完的判断从文件来：某周期的结束日期早于报表业务日期即「已走完」；已走完且未标记发过 → 当天发。
- 无异常发「平稳」绿卡。
- AI 总结只在周报月报跑完时生成，用现有「通知我」通道私聊运营负责人，不进群。
- 待观察名单合并出单监控当天名单，所以顺序在出单监控之后；出单监控失败时用最近一份并在播报台账注明。
- 需要 Node 18+；安装脚本加检查，缺失时给出安装命令。

### 配置

- 新段 `churn`：enabled、mode、webhook_url（回落到 team）、boss_emails、fallback_email（兜底人）、top_n（30）、
  silence_days（[2, 7, 30]）、drop_push（−0.70）、drop_page（−0.50）、weekly_drop（−0.50）、recover_ratio（0.8）、
  gateway_incident_min（3）、agent_owner（可选映射）。全部进配置页字段表，没有密钥。
- 数字读法用现有的容错读法（null / 空串 / 垃圾值回默认，`0` 要留住）。
- 邮箱配置加两条报表规则和 job 的 auto_run 开关。

### 页面「商户流失」

- 生命周期漏斗头部（注册 → 开通 → 首单 → 稳定 → 沉默；入网那级来自出单监控报表的提交 / 通过 / 首笔三个时间）、
  今日命中、沉默名单（按商户分组、站点为行、30 天 TPV 降序、零星型和网关标签）、掉量名单、通道异常、
  周摘要预览、跟进状态、台账缺口提示、「主动清退未剔除」的明示。
- 筛选维度只有一份真相源；顺序走数组不走字典键序；SSE 响应头 `Connection: close`；渲染出来的按钮走事件委托；
  运行状态在 summary 里（沿用 §2.18.5 / §2.18.7 / §2.18.9 / §2.18.95）。
- 首页加入口和待办卡片。

## Testing Decisions

好用例只看外部行为：喂字面量行、拿回去向 / 跃迁 / 文本 / 表行，不看内部怎么算。
每个用例**先让它红一次**（§2.18.99）。行为不该变的地方用逐字节快照比对证明，并记住它证明不了「没漏东西」。

九条缝，四条新开（1、3、5、6），主缝是 3：

| 缝 | 测什么 | 先例 |
|---|---|---|
| 1 一天的运算 `assess(台账若干天, 网关行, 昨日状态, 配置)` | ★ 2 / 7 / 30 各只跃迁一次；恢复归零再沉默重新数；缺口区间不跃迁；多站点不合并；资格在命中时按前 30 算；零星型标签；网关两种标签；通道异常阈值边界；幂等 | 出单监控分类：每行一条去向、传不传 audit 结果相同 |
| 2 两种报表的读取 | 用户ID 不经浮点；站点空格子不变成 `nan`；后来的文件覆盖同一天；缺 sheet 返回原因不返回空表 | 出单监控读表：按名字认 sheet |
| 3 一天的 job `run_day(日期, 附件, 台账目录, 配置, sender)` | 静默 = 不注入 sender；台账文件、表行、群消息、BD 私聊分组、兜底路由、「代理商：」标签、同日重跑不重发、`nan` 不出现、运行记录三个词 | 出单监控 pipeline 的 mode 档；碰网络的函数在用例里换掉 |
| 4 调度 | 注册表顺序；到点该跑哪些；补跑串行、除最后一天外静默、上限、失败即停；一个 job 失败不阻塞后面的 | `tests/automation_catchup.py` 整套注入（launcher / recorder / logger / waiter） |
| 5 转化率无头链 | 同一 Dataset 字面量吐出的两条播报和三张表的行与页面逐字一致；周期走完的判断；未走完不发；平稳卡；AI 只走私聊 | `tests/dataset.mjs` / `bitable.mjs` 的桩 |
| 6 周一摘要 | 头条与报表周报行的「上期活跃本期没有」口径一致；在途风险只数本周新进的；掉量单列不混；无人认领 | `tests/watchlist.mjs` 两条播报的分工 |
| 7 出单监控 180 天 | 十二档变十三档逐条钉死；61~180 落点通知+表且消息独立；>180 仅表；对账每行一条 | `tests/order_monitor.py` [3b] |
| 8 配置与路由 | `churn.*` 在字段表里、密钥不回传、数字容错读法、路由快照多了新路由 | `tests/order_monitor.py` [6c] [2e]、`tests/routes.mjs` |
| 9 页面 | 首页入口 → 页面 → 名单 → 切走不丢；配置 tab 改 `churn.*` 当场生效 | `tests/e2e3.py` / `e2e4.py` |

另外两处必须有快照比对：多维表格改键之后单站点商户的行与改键前逐字段相同；
转化率 job 对同一份报表的输出与页面播报逐字节相同（用 `$WB_FIXTURES` 里的真实报表，不进仓库）。
